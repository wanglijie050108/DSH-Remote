## 缺陷修复

### ① 鸿蒙 `Hello.ets`：cryptoFramework 签名格式与密钥恢复（真机 hello 失败根因）

- **官方文档证实**：Crypto Architecture Kit 的 `sign`/`verify` 接口**仅支持 DER 格式**（华为开发者文章「ECDSA签名 r‖s 和 DER 格式互转」）；旧注释「输出裸 r‖s，经 DerEcdsa 转 DER」是错误假设——真机实测 `sign()` 输出 71~72B DER，误走 `rawToDer` 按 64B 对半切 → 自测报 `BAD_RAW raw len=71`。修复：native 输出直接透传（附 `0x30` 哨兵，平台行为变更时报清晰错误而非发坏包上桥）；`verify` 同理直接喂 DER（`DerEcdsa.ets` 保留为纯逻辑参考实现，`SelfTest` 的 `runDerSuite` 不受影响）。
- **`convertKey` 单材料约束**（官方文档「只包含公钥或私钥的 KeyPair」）：只传 PKCS8 私钥恢复 → `pubKey` 为 undefined → `buildAppHello` 首步 `getPubB64u()` 即崩（日志缺 `harness init：phone_id=` 行即此因）。修复：`PhoneIdentity` 分离持有 pri/pub，新增 `fromPkcs8AndSpkiDer(priDer, spkiDer)`（convertKey 参数序：**公在前、私在后**）；`HarnessService` 持久化 `identity_pkcs8_b64` + `identity_spki_b64` 两份，旧数据（仅私钥）启动时自动重新生成并提示需重新配对。
- **`getEncodedDer` 取值勘误**：API 12–24 公钥仅支持 `'X509|COMPRESSED'/'X509|UNCOMPRESSED'`，代码所写 `'SPKI'` 是无效参数（401）。`'X509|UNCOMPRESSED'` 即 SPKI + 无压缩点 = 契约 pub 形态（与向量 `pub` 逐字节比对通过，91B）。私钥侧 `'PKCS8'` 本就合法，保留。
- **`runHelloVectors` 第⑤步重设计**：PEM 恢复无公钥，无法导出 SPKI 与向量 pub 比对 → 改为 `generate-export-roundtrip` 用例（生成身份的 SPKI 导出须为 91B 标准前缀 + 该导出可直接参与验签往返）。

### ② 鸿蒙 `QrPair.ets`：畸形粘贴输入崩 UI

`decodeQueryComponent`（`decodeURIComponent`）对畸形百分号编码（实测 `127.0.0.1%dshlink://…`，输入残留拼接所致）抛 `URIError`，`parsePairQr` 无捕获 → jscrash 整个 App。修复：解码逐参 try/catch → `BAD_ENCODING`，走既有「QR 解析失败」日志路径。

### ③ 鸿蒙 `DshWebPage.ets` + `HarnessService.ets`：DSH 页面 401

`pairFromQr` 解析后丢弃 QR 的 `t=`（launch token）→ DSH 页面裸加载 `http://127.0.0.1:13080` 被 dsh 拒绝（"authentication required"）。修复：`PairState` 新增 `launchToken`（含持久化），DSH 页面带 `?token=<t>` 加载。注意 token 随 dsh 进程轮换，重启 dsh 后需重新配对（与契约一致）。

### ④ `fake-bridge.mjs`：限流计数器永不清零 → 长连接必僵尸化（并连带 dsh exit 1）

限流注释写「粗粒度 2s 窗口」，但 `ls.count` **只增从不清零**（60s sweeper 只查 silent 连接）：每连接第 41 条消息起永久 `RATE_LIMITED` 且连接不关——两端都靠 25s ping 维持，实测配对后 **~16 分钟（40×25s）** 准时进入僵尸态：插件与 App 同时刷 RATE_LIMITED、隧道重建的 punch 全部被吞、**dsh 进程 exit 1**、App 停在 BACKOFF。修复：消息处理入口按 2s 窗口复位 `count`（`winStart`）。**已部署 ECS**（`/opt/dsh-bridge/tools/fake-bridge.mjs`，远端备份 `.bak-20260919`，`systemctl restart dsh-signal` 后 active）。

⚠ **本修复踩坑记录（v1 补丁无效）**：第一版写成 `now - (ls.winStart ?? now) >= 2000`——`?? now` 使首条消息差值恒 0、`winStart` 永不初始化、复位分支永不执行，**与未修复等价**（部署后 10 分钟复现 RATE_LIMITED 才发现）。正确写法必须显式判 `winStart === undefined`。已用三种流量模式（25s ping×100 / 50 条 1s 突发 / 300 条 10s 洪泛）离线验证修复版逻辑后二次部署（v2）。

## 实测（Pura 90 模拟器 · HarmonyOS 6.1.1）

| 判据 | 结果 |
|---|---|
| G2 向量自测 | **40/40 通过**（修复前 hello 套件抛 `raw len=71` 整体失败） |
| 粘贴 QR → 配对 | `pair.ok`（bridge 验证手机 hello DER 签名）→ ICE → **READY**（一轮 4s 内） |
| 打开DSH 页 | 真实 DSH UI 带 token 渲染成功（修复前 authentication required） |
| bridge 重启后 | agent 自动重连 + App 免扫码路径恢复 hello.ok ✓（pair-2 因 dsh 换 boot_id 按契约作废，重新粘贴即恢复） |
| 旧数据迁移 | App 首启出现一次「旧数据缺少 SPKI 公钥材料，重新生成」后不再出现 ✓ |
| **长稳（v2 部署后）** | 配对静置 **25 分钟：RATE_LIMITED=0、dsh 存活、隧道重建循环正常**——原缺陷 16 分钟必僵尸化，此前带配对的最长存活纪录 ≤13 分钟，均已超越 ✓ |

## dsh exit 1 判定

伴随僵尸风暴出现过 2 次静默 exit 1（无堆栈）。经 `--require` 退出追踪器（`process.exit`/`exitCode`/信号/beforeExit 全埋点）在修复后的 bridge 上复测 25 分钟**不再复现**；追踪到的一次退出事件 code=0（事件循环排空形态），判定为**僵尸风暴的伴生结果**（隧道重建 churn 与死信令竞态），非独立缺陷。追踪器留存于 `D:/Code/.scratch/exit-trace2.cjs`（`NODE_OPTIONS="--require …"` 挂载），若修复后复发可直接抓现场。

## 交接与遗留

- **真机测试交接**：装新 HAP（`entry/build/default/outputs/default/entry-default-signed.hap`）→ 重启 `dsh web` 拿新码 → 粘贴。真机旧 identity 数据会在首启自动迁移（重新生成一次，需重新配对）。
- **dsh exit 1 根因未完全定罪**：发生于 RATE_LIMITED 僵尸风暴期间，按契约运行期故障不应带走 dsh；计数器修复后风暴源头消失，是否还有独立崩溃路径待长稳数据（当前模拟器静置验证中）。
- 模拟器挂起会冻结 App 定时器（BACKOFF 重连不自愈）——模拟器功耗行为，非缺陷；回前台后手动「免扫码重连」即可。
- 安全组 8080 对 0.0.0.0/0 的收窄仍待拍板（021 遗留）。
