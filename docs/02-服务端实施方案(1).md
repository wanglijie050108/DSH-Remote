## 1. 预期目标

交付一个**单机 Docker Compose 部署**的 presence-only 服务端，承载：

1. **Signal**（Go）：WSS 长连接管理、设备验签、pair 撮合、SDP 中转、TURN 凭证签发、presence；
2. **coturn**：STUN 反射 + TURN 中继兜底（只见 DTLS 密文）；
3. **Caddy**：TLS 终止与 WSS 升级。

**DoD（本部分验收）**：

- [ ] 两端（插件 + fake-phone/真机）上线互见 < 3s；`pair.bind` → `pair.ok` < 1s（均为**典型值**；最坏受客户端退避档位影响，见 §7 注）；
- [ ] **W2 的 relay-only 全链路**（打洞强制失败）仍通 —— 注意 **E1 是"大响应字节保真"，不是本项**（v1.1 曾误写）；
- [ ] **`max-bps`（单会话）与 `bps-capacity`（整机合计）限速生效，且能被分别观测**；
- [ ] **按真实客户端 IP（`X-Forwarded-For` 最右一个元素）** 的连接数/消息频率限流生效（`error RATE_LIMITED` 可复现）；
- [ ] **pair 生命周期 8 项语义正确**：①手机断开 → pair 保留；②插件侧抖动（`boot_id` 相同）→ 保留并免扫码重建；③**DSH 重启（`boot_id` 不同）→ 销毁 + `AGENT_RESTARTED`**；④显式 `bye` → **立即销毁 + `bye.ok` + 转发对端**；⑤**宽限期 T=24h 超时 → 销毁 + `PAIR_EXPIRED`**；⑥新设备替换 → `PAIR_REPLACED`；⑦**踢旧连接不得误删新挂载的 pair**；⑧**四个销毁条件全部主动推送给在线对端**（不得依赖对方下次 `hello`）；
- [ ] **宽限期与容量**：T=24h 下 **LRU 淘汰离线最久者而不挡新人**；仅当 256 个 pair **全部在线**时才回 `PAIR_LIMIT`；
- [ ] **`hello` 门禁完整**：10s 超时关闭、`proto_ver` 严格校验（不匹配回 `PROTO_VER_UNSUPPORTED`）、nonce 去重窗口 ≥120s；
- [ ] **Bridge 进程重启后**：两端 <3s 自动重连（信令层），pair 随内存清空而消失 → 手机明确收到 `hello.ok{pair:null}` 并提示重新扫码（**状态丢失，属预期**）；
- [ ] 部署文档一页可复现（compose + 配置 + 防火墙清单）。

**非目标**：数据库、多实例/分片、消息持久化、业务中转（Signal 代码路径中**不存在**任何业务字节）、管理后台。

## 2. 架构

```
手机/插件 ──WSS(443)──► Caddy ──► Signal(Go, 8080 内网)
手机/插件 ──UDP/TCP 3478──► coturn（STUN/TURN；relay 端口段 49160-49999/UDP）
                          ▲ 共享 static-auth-secret（同机 compose 内注入）
```

- **无数据库**：全部状态在内存——
  - `agents[agent_id] → conn`、`phones[phone_id] → conn`（**两个方向都要有**，因为销毁通知要投递给"仍在线的对端"，而 pair 记录即将被删）
  - `pairs[pair_id] → {agent_id, agent_boot_id, phone_id, createdAt, agent_online, grace_timer}`
  - `ptok[ptok_hash] → {agent_id, expire_at}`
  - `phoneIndex[phone_id] → pair_id`（app 免扫码重连用；v1.1 漏列）
  - 其中 `agent_id = phone_id` 的取值方式同构，均为 `sha256(pub)`（**不是**证书指纹）
- **容量口径**：信令 ~30KB/conn，2C4G 万级**在线连接**无压力；但**连接数 ≠ 可用配对数**——可用配对数 ≈ `min(relay 端口数 ÷ 2, 中继带宽 ÷ 单会话速率, pair 上限 256)`（v1.1 的"万级在线"易被误读为"能服务万级配对"，此处写清）；
- 唯一资源项是 TURN 带宽 → 凭证 TTL + 限速 + 监控。

### 2.1 pair 生命周期（判据是"同一个 DSH 进程"，不是"连接是否在"）

**销毁共四个触发条件，每一个都 MUST 向仍在线的一端主动推送**（契约 §4.3）：

| # | 条件 | 动作 |
|---|---|---|
| ① | 任一端发 `bye` | 立即销毁 → 回发送方 `bye.ok` → **转发 `bye` 给对端**；对端离线则只回 `bye.ok` 不转发 |
| ② | 同 `agent_id` 重连但 `boot_id` **不同** | 销毁 → 推 `error AGENT_RESTARTED` 给手机 |
| ③ | agent 断开后 **T = 24 小时**内未以相同 `boot_id` 重连 | 销毁 → 推 `error PAIR_EXPIRED` 给手机 |
| ④ | 新设备对同一 agent `pair.bind` | 销毁 → 推 `error PAIR_REPLACED` 给旧手机 |

```
agent 连接关闭
   ├─ 不销毁 pair；置 agent_online=false；**重新起算** T=24h 计时器（不是沿用剩余时间）
   ├─ 广播 presence{peer_online:false}
   ├─ 期内同 agent_id 重连：
   │     boot_id 相同 → 取消计时器、挂载新 conn → 保留 pair ✅（免扫码）
   │     boot_id 不同 → 销毁 → error AGENT_RESTARTED ❌（重新扫码）
   └─ 计时器到期 → 销毁 + 清 ptok → error PAIR_EXPIRED ❌（重新扫码）
```

**四条硬性实现约束：**

1. **禁止在连接关闭回调里销毁 pair。** 插件重连时 Bridge 要"踢旧连接"；若旧连接的 close 回调触发销毁，会把新连接刚挂载的 pair 一并删掉。销毁只能由上述四个条件触发。
2. **pair 的所有权绑定"当前连接"的实例（连接代次 / 连接 id），不能只按 `agent_id` 判定。** 这条同样适用于 **`bye`**：旧代次连接的 `bye` MUST 记为过期并忽略，否则它能杀掉刚挂载的新 pair。
3. **所有销毁通知按 id 解析当前连接投递**：pair 记录里存 `phone_id` / `agent_id`，投递时查 `phones[phone_id]` / `agents[agent_id]` 取**当前** conn（pair 记录即将被删，不能依赖其中的连接引用）。
4. **`boot_id` 必须与 pair 一同保存**；`hello` 中 agent 未带 `boot_id` 或 `proto_ver` 不为 `"1.0.3"` → 回 `error` 并关闭。

> **为什么不能用"断开时长"当判据**：插件身份密钥是持久化的，DSH 重启后插件带**同一个 `agent_id`** 回来；若只按"T 秒内回来了就算抖动"，会把"DSH 崩溃后快速重启"误判成抖动并自动恢复——与"DSH 重启必须重新扫码"的产品语义相反。`boot_id` 把判据从"多久"改成"是不是同一个进程"，时间只剩内存上界作用。

**宽限期 T = 24 小时的产品含义**（契约 §4.3 已写）：①②承担全部语义判断，**T 纯粹是内存上界**，它决定的是「PC 侧离线多久以内手机不必重新扫码」。24h 覆盖合盖/断网/切 VPN；**超过 T 必须重新扫码，与 DSH 是否重启无关**。UX 文案按 §3.2 的 `PAIR_EXPIRED` 区分，避免被当成 bug 上报。

**手机侧断开不销毁 pair**：手机可长期离线，回来凭 `hello.ok{pair}` 免扫码恢复。

### 2.2 容量与淘汰

- **pair 上限 256**（与 TURN relay 端口段匹配，§4）；
- **淘汰策略 = LRU**：`pair.bind` 时若已达上限，**优先淘汰"离线最久"的 pair**（其 agent 已不在线，淘汰无损），而不是对新人回 `PAIR_LIMIT`；
- **仅当 256 个 pair 的 agent 全部在线**时才回 `error PAIR_LIMIT`；
- 理由：T 拉长到 24h 后，"离线但未过期"的 pair 会长期占用配额，若不淘汰会持续挡新人。

## 3. Signal（Go）设计

### 3.1 工程结构

```
remotedsh-bridge/
├─ cmd/signal/main.go
├─ internal/hub/         # 连接管理、pair 表、boot_id 比对、宽限期计时器、LRU 淘汰、TTL sweeper
├─ internal/auth/        # P-256 验签（§4.2 序列化）、pair_token 校验、TURN 凭证签发(HMAC-SHA1)
├─ internal/limit/       # per-IP 连接数、消息速率、帧大小上限、hello 超时
└─ deploy/               # compose.yaml、Caddyfile、turnserver.conf、防火墙清单
```

### 3.2 协议实现要点（契约 §4）

- WS 端点 `/v1/signal`，读写 JSON 文本帧；入站帧上限 **64KB**（SDP 充足）；**出站转发的 `sdp` 也 MUST 校验为字符串且不超过同一上限**，防止一端让服务器放大；
- **`t` 是封闭集合**：按契约 §4.1 做 `switch`，**`default` 直接以 `error` 拒绝并关闭连接**。永远不要新增"通用转发"类型——presence-only 的"代码路径中不存在业务字节"这一保证完全依赖这条规则；
- **`hello` 门禁**：连接建立后 **10s** 内未收到合法 `hello` → 关闭；校验顺序为 ①`proto_ver == "1.0.3"`（否则 `PROTO_VER_UNSUPPORTED`）②时间窗 ±60s ③nonce 去重（窗口 ≥120s）④验签（**按契约 §4.2 的规范化字节串**：UTF-8 `"hello|" + ts十进制 + "|" + nonce`，`sig` 为 **DER** → base64url）；
- `hello` 通过后：agent 按 `agent_id` 存 `agents[id] → conn`（**含 `boot_id`**），app 按 `phone_id` 存 `phones[id] → conn`；**同 id 重复上线 → 踢旧连接**（按 §2.1 约束 1/2 处理，踢旧不得触发销毁，旧连接的后续 `bye`/帧一律按过期丢弃）；
- `pair.ready` → 存 `ptok[hash]` 并回 **`pair.ready.ok`**（插件必须收到它才出 QR）；同一 agent 重新注册时作废旧 hash；
- `pair.bind`：比对 hash 与 TTL → 若已有 pair 走 §2.1 条件④ → **每 agent 至多 1 个 pair** → 若达上限按 §2.2 **LRU 淘汰** → 创建 pair → **双端各发 `pair.ok`**（含 TURN 凭证块）；
- 重连：app 侧 `hello` 后按 `phone_id` 查 `phoneIndex` → `hello.ok{pair}` 非空即免扫码重连；agent 侧按 `agent_id` 查 pair 并执行 §2.1 的 `boot_id` 比对；
- `punch.request`：**先检查 agent 在线**；离线（宽限期内）→ 回 `error PEER_OFFLINE`，**不得静默丢弃**；
- `punch.offer/answer`：只做对内转发（校验 `pair_id` 归属，**绝不跨 pair 路由**；断言失败回 `error PAIR_NOT_FOUND` 并告警）；**不解析 SDP 内容**；`punch.offer` 发给离线手机 → 回插件 `error PEER_OFFLINE`；**对"插件自发重发"做 ≥2s 最小间隔限流（窗口内丢弃），但由 `punch.request` 触发的 offer MUST NOT 被该窗口丢弃**；
- 心跳：`ping`/`pong` 应用层消息；60s sweeper 判离线（**半开连接只靠它发现**）并广播 `presence`；**sweeper 判离线与连接 close 走同一条 GRACE 流程**（都置 `agent_online=false` 并重新起算 T）；`presence.get` 以当前状态应答，初始值随 `hello.ok` 下发；
- **`bye`**：消费（不直接转发原消息）→ 立即销毁 pair → 回发送方 `bye.ok` → 向对端**转发** `bye`（对端离线则只回 `bye.ok`）；
- **TURN 凭证**：`username="<expire>:<pair_id>"`、`credential=base64(HMAC-SHA1(secret, username))`、TTL 3600s（契约 §5）；`relay.request` → `relay.alloc` 应答。**"续期"不维持已有隧道**——已建立的 allocation 由客户端 Refresh 维持，不会因凭证过期而断；签发新凭证产生**新 username**（在 coturn 眼里是新用户），**不能延长已有 allocation**。因此 Bridge 只在客户端明确 `relay.request` 时签发；
- 日志：结构化（zap）——pair 生命周期（含 `boot_id` 比对结果与销毁原因）、punch 结果（p2p/relay、耗时）、凭证签发、限流命中；**不记录任何 SDP 以外内容，SDP 也仅记指纹字段用于排障**。

### 3.3 限流与防滥用

| 项 | 值 | 说明 |
|---|---|---|
| 单 IP 连接数 | ≤ 16 | **IP 取 `X-Forwarded-For` 的最后一个元素**；且**只在确实配置了 `trusted_proxies` 时才采信该头**（见 §5 的正确心智模型） |
| 消息速率 | ≤ 20 msg/s/conn | 超限回 **`error RATE_LIMITED`**（契约 §4.5 的字符串码；WebSocket 握手后没有 HTTP 状态码） |
| `hello` 超时 | 10s | 未收到合法 `hello` 即关闭 |
| nonce 去重窗口 | ≥120s | 必须 ≥ 验收时间窗（±60s）+ 时钟偏移，否则被淘汰的窗口内可重放 |
| pair_token 尝试 | 连续 5 次失败锁该 IP 10min | 防猜 token。IPv6 下攻击者可轮换地址，per-IP 锁定只作辅助；真正屏障是 32B 随机 |
| 单实例 pair 上限 | **256** + **LRU 淘汰** | 见 §2.2；仅全在线时回 `PAIR_LIMIT` |
| `punch.offer` 间隔 | ≥2s / pair（**仅限插件自发重发**） | 防抖动导致手机反复拆建 PeerConnection；由 `punch.request` 触发的不受限 |

> **直连 8080 的处理**：Signal 仅 compose 内网 `expose`，不对公网。若仍收到非 Caddy 网段的连接，以 TCP 对端地址计并**告警**（说明部署被改坏）。

## 4. coturn 配置（`turnserver.conf` 关键行）

```conf
listening-port=3478
fingerprint
lt-cred-mech                    # 必须。coturn 文档：WebRTC 必须启用长期凭证机制，
                                #   "WebRTC relaying will not work with anonymous access"
use-auth-secret
static-auth-secret=<S>          # 与 Signal 同源注入（compose secret）
realm=<domain>
min-port=49160
max-port=49999                  # 840 个 relay 端口：全 TURN 最坏 2 端口/对 → 支撑 420 对，与 §2.2 pair 上限 256 匹配
no-tls
no-cli
max-bps=6250000                 # 单会话带宽上限 ≈50Mbps（6.25MB/s）
bps-capacity=25000000           # 整机合计带宽上限 ≈200Mbps（≈4 个满速会话）；此参数是全局总量，不是单用户
stale-nonce=1200
external-ip=<公网IP>/<内网IP>    # NAT 环境（云主机）必须
log-file=/var/log/turn
simple-log
```

**注意不设 `no-tcp`**：契约 §5 的 `uris` 含 `turn:<host>:3478?transport=tcp`，用于 UDP 被封网络的兜底（`no-tls` 只关闭 5349 的 TLS/DTLS 监听，不影响 3478 的 TCP 监听）。**5459/`turns:` 不在 v1 范围。**

- **`max-bps` 与 `bps-capacity` 的区别必须写清**（v1.0 曾把后者注释成"单用户上限"）：前者是**单会话**，后者是**整机合计**。二者都要能被分别观测。
- **`user-quota` 若设置 MUST ≥2**：契约 §5 下两端拿到的是**同一个 coturn 用户名**（`username = "<expire>:<pair_id>"`），设成 1 会让第二端分配失败。当前未设（采用 coturn 默认不限）。
- 用量观测：coturn 的 session/bytes 日志按 `username`（含 pair_id）统计 → 每对 ≤ 200MB/天 由**部署侧脚本告警**执行（coturn 原生无按天配额，Phase 1 用监控 + 人工处置）。
- 若启用 `--prometheus`（9641）：**不要开 `--prometheus-username-labels`** —— coturn 文档明确警告，用 username 做 label 在"ephemeral usernames（如 TURN REST API）"下会导致内存泄漏，而本方案正是每对一个临时 username。
- `log-file` 接受目录还是文件名各版本示例不一致，部署时实测确认（容器内还需确认挂卷可写）。

## 5. Caddy 与 Compose

```caddyfile # Caddyfile
<domain> {
  encode zstd gzip
  reverse_proxy /v1/signal signal:8080
}
```

```yaml # compose.yaml（骨架）
services:
  caddy:
    image: caddy:2
    ports: ["443:443", "80:80"]
    volumes: [./Caddyfile:/etc/caddy/Caddyfile, caddy_data:/data]
  signal:
    build: ./cmd/signal
    environment: [TURN_SECRET=${TURN_SECRET}]
    expose: ["8080"]            # 仅内网；暴露到公网会让"单 IP ≤16"退化为"全站 16 连接"
  coturn:
    image: coturn/coturn
    network_mode: host          # TURN 推荐 host 网络（relay 端口段 + external-ip）
    volumes: [./turnserver.conf:/etc/coturn/turnserver.conf:ro]
volumes: { caddy_data: {} }
```

> `TURN_SECRET` 用 compose secret 或 `.env`（0600）注入 Signal 与 coturn 两处，属部署物，不入库。

### 5.1 真实客户端 IP 的正确心智模型（v1.1 的论证已修正）

Caddy 官方文档原文：

> "By default, Caddy passes through incoming headers—including `Host`—to the backend without modifications, with three exceptions: It sets or augments the `X-Forwarded-For` header field… **For these `X-Forwarded-*` headers, by default, the proxy will ignore their values from incoming requests, to prevent spoofing.** If Caddy is not the first server being connected to by your clients (for example when a CDN is in front of Caddy), you may configure `trusted_proxies`…"

因此：

1. **默认（无 `trusted_proxies`）**：Caddy **丢弃**入站 `X-Forwarded-*` 值，写入客户端地址 → Signal 收到的 XFF 只有 Caddy 写入的元素；**取最右（=唯一一个）正确**；
2. **本方案 MUST NOT 配置 `trusted_proxies`**，除非 Caddy 前面真的还有一层可信代理。**v1.1 文稿里"客户端可伪造 XFF，所以取最左是错的"这个前提是不准确的** —— 而按那个心智模型去配 `trusted_proxies private_ranges`（以为"这样才对"）时，若客户端本身就在私网，**反而会真的让伪造值生效**；
3. 若将来在 Caddy 前加了可信代理，规则变为"按可信跳数从右往左取"，且 **MUST** 用 `servers > trusted_proxies` 全局选项而非 per-proxy 配置。

> 结论不变（取最右），但**理由与配置注意事项**按本节执行。

## 6. 部署清单

1. 域名 + DNS A 记录；**境内服务器需 ICP 备案【开放决策，见 §10】**；
2. 防火墙/安全组放行：`443/tcp`（WSS）、`3478/udp` + **`3478/tcp`**（STUN/TURN，TCP 是 UDP 被封时的兜底）、`49160-49999/udp`（relay 段）；
3. **真实 IP（必做）**：按 §5.1 执行；Signal 8080 仅 compose 内网 expose、不对公网；
4. 证书：Caddy 自动 Let's Encrypt（境外/已备案域名）；否则自签 + 客户端 pin（增加分发成本，不推荐）；
5. `docker compose up -d`；冒烟：`wscat -c wss://<domain>/v1/signal` 应在 10s 内收到 `error`（缺 hello 或超时）即通；
6. 重启预案：`docker compose restart` —— 两端信令 <3s 重连；**pair 随内存清空而消失**，手机提示重新扫码（**状态丢失，属预期，非故障**）。

## 7. 测试计划

| 层 | 内容 | 方法 |
|---|---|---|
| 单元 | 验签（好/坏签名/过期 ts/nonce 重放/**签名串序列化**）、`proto_ver` 校验、`boot_id` 比对、token 校验、宽限期计时器重新起算、LRU 淘汰、TURN 凭证 HMAC | `go test` + **与插件/APP 共用 `hello` 签名向量** |

## 10. 风险与开放项

| 风险/开放项 | 处理 |
|---|---|
| TURN 流量成本 | 凭证 TTL 1h + `max-bps`（单会话）+ `bps-capacity`（整机）+ 每对用量日志告警；配额自动切断列 N 阶段 |
| 境内部案 vs 境外部署 | **仍开放**（v0.4 §12）；W2 公网部署前必须拍板 |
| coturn 被滥用为公共中继 | 凭证必须由 Bridge 签发；无 pair 无凭证；relay 端口段最小化 |
| 单点 | 接受（presence-only，业务不经过服务器）；重启预案 + 客户端退避重连（**Bridge 重启 = 重新配对，属预期**） |
| 云主机 NAT（`external-ip` 配置错误 → 打洞/中继全挂） | 部署清单显式项 + W1 LAN 模式先行规避，公网部署后复测 |
| UDP 与 TCP 3478 都被封 | `uris` 含 `?transport=tcp` 覆盖前者；后者需开 5349/`turns:`（需证书），列为后续变更 |
| XFF 采信策略被误配 | §5.1 写死"默认不配 `trusted_proxies`"；集成测试覆盖伪造 XFF 场景 |
