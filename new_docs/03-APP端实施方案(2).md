## 1. 预期目标

交付 Android 薄壳 App **`remotedsh-android`**，实现：

1. 扫码配对（解析契约 §2 的 `dshlink://pair` QR，完成设备密钥签名绑定）；
2. WebRTC 隧道客户端（P2P 优先、TURN 兜底，DTLS 指纹 pin 插件）；
3. 本地代理（`127.0.0.1:13080`，L4 字节透传，不解析 HTTP）；
4. WebView 加载 DSH 官方 GUI——真机完整跑通四功能（列会话/看历史/发消息/审批作答）。

**DoD（本部分验收）**：

- [ ] 真机（蜂窝）出画面、登录、刷新/杀 App 重进仍保登录态（cookie 持久，前提是 authority 不变）；
- [ ] 审批端到端（前台）拆两条独立指标：**(a) PC 触发 → 手机卡片出现 < 1.5s**；**(b) 手机作答 → DSH 继续 < 1.5s**；
- [ ] WS 30 分钟 0 断连（E2 真机复测，**亮屏前台**——本部分不做前台服务常驻）；E1 真机 harness 通过（`adb forward` 字节保真，见 §5）；
- [ ] **pin 红线在任何路径下都成立**：首次配对、**免扫码重连（App 重启后）**、插件主动重发 `punch.offer`、隧道重建——**每一次 `setRemoteDescription` 之前都执行校验**；offer 中无 `sha-256` 行 → 立即中止；
- [ ] **凭证路径完整**：任何一次新 gather 之前（首次、免扫码重连、网络切换、隧道重建）若本地无有效 TURN 凭证或剩余 TTL 低于阈值，先 `relay.request` → `relay.alloc` 再建 `PeerConnection`；
- [ ] **信令心跳义务**：每 **25s** 发 `ping`；60s 无帧被判离线后能自行重连；
- [ ] E4 明文策略结论落表（三台真机：原生 Android + 任一国产 ROM + 平板）；E7 走查报告（含平板横屏视口）；
- [ ] 扫码 → 可用 ≤ 30s；**错误文案按原因区分**：`AGENT_RESTARTED`（DSH 已重启）/ `PAIR_EXPIRED`（PC 离线超过 24 小时）/ `PAIR_REPLACED`（已在另一台设备配对；主动换绑场景忽略，见 §3.3）各自给出不同提示，**均不静默失败**；网络抖动恢复的场景**不得**要求重新扫码；
- [ ] **长中断恢复**：隧道中断超过 **10s** 后重建完成时，MUST 主动 `webView.reload()`（见 §4）。

**非目标（本部分）**：原生业务 UI、推送、前台服务常驻（仅 E9 实验临时用）、iOS/鸿蒙、多设备管理。

## 3. 模块设计

```
remotedsh-android/
├─ core-contract/   # 帧编解码（引用 remotedsh-contract 共享测试向量）
├─ core-rtc/        # PeerConnection 封装 + DTLS 指纹 pin + 双 DataChannel
├─ core-proxy/      # 本地 TCP 代理（127.0.0.1:13080）
├─ core-pairing/    # QR 解析、Keystore 签名、配对状态存储
├─ core-bridge/     # 信令 WSS 客户端（心跳、退避重连、消息分发）
└─ app/             # 三屏 + WebView 壳 + 状态机
```

### 3.1 core-rtc

- `RtcCertificatePem`：首次启动生成 P-256 证书 PEM，加密持久化——DTLS 指纹跨启动稳定。**W1 需确认该证书的注入点**（`PeerConnectionFactory` 还是 `RTCConfiguration`）；
- `PeerConnection` 配置：iceServers 来自 `pair.ok.turn` / `relay.alloc.turn`（`stun:` + `turn:?transport=udp` + `turn:?transport=tcp`）；**单阶段 ICE**——首次 gather 即含 relay 候选，P2P/TURN 由 ICE 并行探测自动择路，**不存在"3s 失败后二次切换"**；
- **两条 DataChannel 由插件（offer 方）创建**，手机作为 answerer 通过 `onDataChannel` **接收两条**（`data` 有序可靠 / `ctl` 无序可靠，见契约 §3）。**手机 MUST NOT 自己 `createDataChannel`**——那会触发重协商，而契约的消息表不含 app→agent 的 offer。若只收到一条或通道参数不符 → 视为协议错误，断开并记录；
- **pin 校验点（红线）**：**每一次 `setRemoteDescription` 之前**执行，算法 MUST 与契约 §6.1 逐字一致：
  1. 取 offer SDP 的 `a=fingerprint` 行；**多行时取 `hash-func` 归一后等于 `sha-256` 的那一行**（RFC 8122 §5.1 允许多行，其示例同时含 SHA-256 与 SHA-1；取到 `sha-1` 行会永不匹配）；行可位于 session 级或 media 级，**冲突时以 media 级为准**；
  2. **强制归一**：**剥掉 `hash-func` 前缀 → 删除全部冒号与空白 → ASCII 小写 → 按字节比较**（确定性算法，不允许"可选忽略冒号"——否则两端可归一出不同结果）；
  3. 与**本地持久化的 `fp`** 比较（§3.3）。**不得**与"内存里的 QR 内容"比较 —— App 重启后 QR 已不在手上，免扫码重连将无法校验；
  4. 不一致或**不存在 `sha-256` 行** → **立即中止，MUST NOT 继续 `setRemoteDescription`**（fail-closed），置错误态"对端身份校验失败"；
- **反压（App 侧同样要落实）**：`onMessage` 是推送式回调，**没有"停止读取"的 API**。因此：① 用**契约自带的 `WINDOW` 信用**让对端停发（本地 socket 排水后才回填）；② 限制本地未发送队列（单流 `bufferedAmount` ≤256 KiB、全局 ≤512 KiB，用 `bufferedAmountLowThreshold` 驱动恢复）；③ **红线：绝不在 WebRTC 回调线程里阻塞写 socket**——`onMessage` 里只入队，实际写 socket 在独立协程中完成；
- 事件回调：`onConnectionChange`/`onIceConnectionChange`（**隧道重建的主触发**，契约 §3.5）、`onFailed`/`onDisconnected` → 驱动状态机。

### 3.2 core-proxy

- `ServerSocket` 绑定 **`127.0.0.1:13080`**（= 契约 §1 的 authority，也是 WebView 发出的 `Host`）；
  - `BindException` → **硬失败**，UI 提示"本地端口 13080 被占用，请关闭占用它的应用并重试"。**不做端口回退**：cookie 名由 authority 派生，换端口会使全部 cookie 失效，与 DoD 冲突；
- 仅接受 loopback 来源（`socket.inetAddress.isLoopbackAddress`），否则立即关闭。**这是防御性检查，不是安全边界**：Android 上应用之间没有 loopback 隔离，同机其他 App 也能连到该端口。真正的边界是 DSH 的浏览器 cookie（`HttpOnly`，存在 WebView 的 CookieManager 中）与配对本身；
- 每连接一个协程：读 socket → 按契约 §3 切帧（`len ≤ 16373`）→ 信用记账（初始 256 KiB **每方向**、WINDOW 回填 **≥64 KiB 且值为"自上次 WINDOW 以来实际写入的字节数"**、并发 stream 上限 128）；
- **流状态机按契约 §3.3 实现**，尤其**收到 `FIN` 只做半关闭（`shutdownOutput`），继续读**——否则 HTTP 响应体会被静默截断；
- WS 长连接即普通流：升级请求与其后全部帧同一条 stream 保序透传（红线：不吞 DSH 2s Ping、不做 UTF-8 转换）；
- **隧道未就绪时对新建本地连接的处理：立即 `close()`，不排队、不缓冲**（DSH 前端在断线期间会按退避不断重建 TCP 连接，排队会在隧道里堆一批半死的流）；
- App 生命周期：进入后台**不主动关代理**。**"系统冻结后 socket 由内核保持"不是可靠假设**：进程被冻结时内核可能仍持有 socket，但 Doze/App Standby 会切断网络，且 OEM 后台策略随时可能杀进程——两种情况下隧道都会在保活超时后死亡。Phase 1 不对抗（无前台服务），回来后走 §4 的重建流程。

### 3.3 core-pairing / core-bridge

- 扫码 → 解析 `dshlink://pair` → 校验 `v` 与必填字段 → 持久化（见下表）→ WSS 发送：

  ```
  hello{role:"app", pub(SPKI DER→base64url), ts, nonce, sig, proto_ver}
  pair.bind{ptok}
  ```

  - **`pub` 必须带**（契约 §4.1）：它既用于 Bridge 验签，也是 `phone_id = sha256(pub)` 的唯一来源，而 `pair.bind` 已不带密钥材料——**漏掉 `pub` 会必然 `AUTH_FAILED`**（v1.1 的漏写已修正）；
  - **`hello` 序列化 MUST 严格按契约 §4.2**：`ts` = epoch 秒（十进制整数）、`nonce` = 32B→base64url（每次新生成）、被签名串 = UTF-8 `"hello|" + ts十进制 + "|" + nonce`、`sig` = ECDSA P-256/SHA-256 的 **DER** 编码 → base64url。**三端共用 `remotedsh-contract` 里的签名测试向量**；
  - `proto_ver` = `"1.0.5"`；收到 `PROTO_VER_UNSUPPORTED` → **提示升级客户端，MUST NOT 重试、MUST NOT 提示重新扫码**（重扫码解决不了版本偏差）；

- **存储清单（必须完整，v1.1 缺三项）**：

  | 键 | 为什么必须存 |
  |---|---|
  | `sigURL` | 重连信令地址 |
  | `authority` | 手机侧固定端口（`127.0.0.1:13080`） |
  | **`fp`（插件证书指纹）** | **pin 红线要能与"本地持久化的 fp"比较**；不存则 App 重启后的免扫码重连**无法校验对端身份**（而契约允许插件任意时刻重发 offer，窗口很大） |
  | **`agentId`** | 显示/日志/多设备预留（**不参与校验**） |
  | **TURN 凭证 + 到期时间** | 免扫码重连与新 gather 都要 iceServers；只从 `pair.ok` 取、不持久化 → 重连时 **iceServers 为空**（连 STUN 都没有），`?transport=tcp` 兜底彻底失效 |
  | 设备公钥别名 | Keystore 别名 |

  **不存**：`ptok`（用后即弃）、任何 DSH cookie（归 WebView CookieJar，`HttpOnly` 本来也读不到）；

- **心跳义务**：WSS 连接期间每 **25s** 发 `ping`（契约 §4）；60s 无帧会被 Bridge 判离线并广播 `presence{peer_online:false}`——**App 不发心跳会造成"自己在线上却被判离线"**，与 §3.3 的 `PEER_OFFLINE` 分支自相矛盾；
- 重连规则（契约 §4.3/§4.5，文案必须区分）：
  - App 重启 → `hello` → `hello.ok{pair 非空}` → **若本地凭证无效/临近过期先 `relay.request`** → `punch.request` → offer/answer 重建（**免扫码**）；
  - `hello.ok{pair:null}` 或 `error PAIR_NOT_FOUND` → "请重新扫码"；
  - `error AGENT_RESTARTED` → "**电脑上的 DSH 已重启，请重新扫码**"；
  - `error PAIR_EXPIRED` → "**PC 离线超过 24 小时，配对已失效，请重新扫码**"；
  - `error PAIR_REPLACED`（发送方恒为 Bridge，非对端设备）→ 手机是被动方（被新手机挤掉，本地无更新的绑定）："已在另一台手机完成配对" + 清本地配对信息；手机是主动方（用户扫了新电脑的 QR 完成换绑——Bridge 因这次 `pair.bind` 销毁旧 pair 而推送的 `PAIR_REPLACED` 可能先于新 `pair.ok` 到达）：此时本地已绑定新电脑，**忽略该错误**（不清新配对、不提示）——以本地最新绑定的 agent 为准；
  - `error PEER_OFFLINE` → **不断开、不清配对**；保持连接，等 `presence{peer_online:true}` 后自动重试 `punch.request`；
  - `error PROTO_VER_UNSUPPORTED` → 提示升级，**不重试**；
  - `error PAIR_LIMIT` → **提示"服务繁忙"，不自动重试**（超限直接拒绝、不做 LRU 淘汰，契约 §4.5，用户 2026-09-13 决策）；
  - `error RATE_LIMITED` / `INTERNAL` → 指数退避；
  - 收到 **`bye`**（对端主动解除）→ 清本地配对信息 → 置 NEED_PAIR → 提示重新扫码；
  - **本端主动解除（用户操作）** → 发 `bye{reason:"user"}` → **等待 `bye.ok`（超时 2s）** → 拆 `PeerConnection`/`DataChannel` → 清本地配对信息（`fp`/凭证/设备别名）→ 置 IDLE；**不得只清本地状态而不通知 Bridge**（否则服务端 pair 残留，下次连上会静默恢复用户以为已撤销的配对）；
  - 以上除 `PEER_OFFLINE` 外**均必须显式提示，不静默重试**；
  - **本地隧道拆除义务**：所有进入 NEED_PAIR 的路径（`bye` / `AGENT_RESTARTED` / `PAIR_EXPIRED` / `PAIR_REPLACED` 被动方 / `PAIR_NOT_FOUND`）MUST 同时拆毁当前 `PeerConnection`/两条 `DataChannel` 与本地代理既有流；**主动换绑（扫新 QR）时在持久化新配对之前先拆旧隧道**——旧 agent 侧会因条件⑤自行拆除，勿依赖对端清理；
  - WSS 断 → 指数退避 500ms→30s + 抖动；
- 打洞（**单阶段 ICE**）：**先确保凭证有效**（必要时 `relay.request`）→ 发 `punch.request` → 收 `punch.offer`（已含 host+srflx+relay 候选）→ **pin 校验** → `createAnswer` → `punch.answer` → ICE 并行探测自动择路；**随时接受插件主动重发的 `punch.offer`**（幂等替换当前连接）；契约规定**插件自发重发之间 ≥2s**，App SHOULD 忽略更短窗口内的重复 offer；
- **隧道重建**：主触发 = `connectionState`/`iceConnectionState` ∈ {disconnected, failed}（契约 §3.5）；`stream_id` 重建后从 1 重启。

### 3.4 app 壳（三屏 + WebView）

| 屏 | 内容 |
|---|---|
| 扫码屏 | 相机取 QR → 进入配对；已有配对信息则显示"上次设备"一键重连 |
| 状态屏 | 状态机可视化（见 §4）；失败原因与"重新扫码"入口 |
| WebView 屏 | 固定地址壳 |

WebView 配置清单（安全红线）：

```kotlin
webView.settings.run {
    javaScriptEnabled = true
    domStorageEnabled = true          // 官方前端 localStorage 需要
    allowFileAccess = false
    allowContentAccess = false
}
WebView.setWebContentsDebuggingEnabled(BuildConfig.DEBUG)   // release 关闭
cookieManager.setAcceptCookie(true)                          // 接受并定期 flush()
// 禁止任何导航离开 127.0.0.1：shouldOverrideUrlLoading 拦截非 loopback host
webView.setSupportMultipleWindows(false)                     // 挡 window.open / target=_blank
// WebChromeClient.onCreateWindow 一律返回 false；setDownloadListener 拒绝（DSH 有 /export 下载入口）
```

- **token 交换**：`GET http://127.0.0.1:13080/?token=<QR 中的 t>` → DSH 返回 **303 + Set-Cookie** → 此后固定 `loadUrl("http://127.0.0.1:13080/")`；
  - 该 URL 的**实际约束**（已按源码核实）：方法必须是 `GET`、`pathname` 必须**恰好**是 `/`、名为 `token` 的参数必须**恰好一个**。**其他查询参数不影响**（v1.1 写成"多一个参数就 401"过严）；
- **「QR 里没有 `t`，本地也没有 cookie」的路径（必须实现）**：`t` 是可选字段。
  1. 直接 `loadUrl("http://127.0.0.1:13080/")`；
  2. 用 `WebViewClient.onReceivedHttpError` 捕获 **401**（判定"有无有效 cookie"最可靠的方式，比读 CookieManager 稳）；
  3. 收到 401 → 进入状态屏，提示"本地登录已失效，请在 PC 上用 `dsh web` 重新生成带 token 的二维码后重新扫码"。不要反复重试，也不要停在白屏；
  - **注意**：01 §6 已改为插件通过 `ctx.connection.authenticatedUrl()` **程序化取 token 并写入 QR**，因此正常路径下 QR **总是带 `t`**，本分支只在异常时发生；
- **明文豁免**：`res/xml/network_security_config.xml`——v1 用 `base-config cleartextTrafficPermitted="true"`（NSC 对 IP 字面量的 domain 匹配性【E4 实测确认，支持则收窄到 `127.0.0.1`】）。
  - **注意**：`base-config` 是**全 App 放行明文**。若 E4 证明 IP 字面量可用 `<domain>`，**必须收窄**；若不可用，则加一条硬约束：**除 loopback 外，App 不得发起任何明文请求**。

## 4. 状态机（连接与降级）

```text
IDLE →(扫码/重连)→ SIGNALING →(pair.ok)→ PUNCHING
PUNCHING →(ICE 通，自动择路 P2P 或 TURN)→ CONNECTED ──keepalive/ICE 丢失──► RECONNECT（<5s 目标）
任一态 →(hello.ok{pair:null} / PAIR_NOT_FOUND)→ NEED_PAIR（"请重新扫码"）
任一态 →(AGENT_RESTARTED)→ NEED_PAIR（"电脑上的 DSH 已重启，请重新扫码"）
任一态 →(PAIR_EXPIRED)→ NEED_PAIR（"PC 离线超过 24 小时，配对已失效，请重新扫码"）
任一态 →(PAIR_REPLACED，被动方)→ NEED_PAIR（清本地配对信息）；主动换绑方（本地已绑定更新 pair）→ 忽略（§3.3）
任一态 →(收到 bye)→ NEED_PAIR（对端主动解除）
任一态 →(PROTO_VER_UNSUPPORTED)→ 提示升级，停止重试
任一态 →(PEER_OFFLINE)→ 保持连接，等 presence 恢复后自动重试
网络切换（ConnectivityManager 回调）→ 主动 RECONNECT（不等待心跳超时）
```

**隧道重建的三条触发器**（契约 §3.5）：① 主触发 = ICE/`connectionState` ∈ {disconnected, failed}；② 兜底 = 5s PING / **15s 无帧**；③ 网络切换回调。

**自愈窗口是有限的，必须按实际数字设计**：DSH 前端退避 `500ms / ×2 / max 10s`，走到最后一档会 `emitState("disconnected")` 并**无限等待**，只有"手动 `reconnect()`、系统网络状态变化、`stop()`"三者之一能唤醒 —— 累计约 **12.75–25.5 秒**后前端停住。因此：

| 情形 | 结果 |
|---|---|
| 隧道在 **~10s 内**恢复 | 前端自愈，用户只感到 1–2s 卡顿 |
| 隧道在 **>10s 后**才恢复 | 重建完成时 App 主动 `reload()`，用户多等一次页面加载（1–2s），会话不丢 |

而 ICE 的 `failed` 受 RFC 7675 consent 约束（约 ≤30s，实现相关），**可能晚于前端停车**。因此：

- **`webView.reload()` 从"锦上添花"升为必需路径**：**隧道中断时长超过 10s 后重建完成时，MUST 主动 `webView.reload()`**（**阈值 10s，用户 2026-09-13 裁决**——必须低于前端最早停车点 12.75s，消除 12.75–30s 的死区；DSH 会话是服务端持久的，重载不丢会话，reload 代价极低、宁可多 reload）。**不得**依赖"读 WebView 内部状态判断是否已恢复"——DSH 没有暴露该 API；
- 备选（若 W1 实测 ICE 上报 ≤10s，可退回）：把兜底收紧为"有活动流时 3s PING / 9s 阈值"，但要评估前端重试间隙造成的误判；
- **`navigator.onLine` / `online` 事件只在手机系统网络状态变化时触发**；隧道断了而手机网络没变时**不会**触发，不能依赖它自愈；
- UI 引导：DSH 的**设置 → 通用**页有重连入口（`connection.reconnect()` 由 `dsh-client-ui-settings-general` 注入）。
