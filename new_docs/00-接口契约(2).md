## 1. authority 与端口约定

| 项 | 值 | 说明 |
|---|---|---|
| authority（手机侧） | `127.0.0.1:13080` | 手机本地代理绑定的**固定**端口，也是手机发出的 `Host`。cookie 名 = `dsh-auth-<base64url(sha256(authority))>`。**v1 只有一个值：不存在备用 authority，也不做运行时切换** |
| 插件侧转发目标 | `127.0.0.1:3080`（默认） | 插件内部 `net.connect` 的目标，**与 authority 是两个独立的值**。插件 MUST 优先取 `ctx.webServer.port`（**不是** `ctx.webServer.host`——该 getter 返回配置值，可能为 `0.0.0.0`），环境变量只作兜底 |
| authority 改动 | **破坏性变更** | 改动 authority = 全体设备 cookie 立即失效（401），需重新扫码并由用户重新下发 launch token |
| PC 侧 DSH 端口改动 | **非破坏性** | 手机侧 `Host` 不变 → cookie 不受影响，只需同步插件的转发目标 |
| OPEN 的 authority 校验 | 一致性断言 | 手机在 `OPEN` 中声明的 authority MUST 等于本节固定值，否则 `RST`。因转发目标固定，此校验**不是** SSRF 防护，只是防止手机与 QR 失配 |

**为什么手机侧用 `13080` 而不是 `3080`**：手机不一定能绑上 3080（可能被同机其他应用占用），13080 是冷门端口。DSH 的 `/api` Host 围栏只校验主机名是否为 loopback（`isLoopbackHostname`），**不校验端口**，因此手机侧端口可自由选择；"PC 侧 DSH 端口改动不影响 cookie"也正源于此。

## 2. QR 配对载荷

```
dshlink://pair?v=1&s=<sigURL>&pt=<pair_token>&fp=<plugin_fp>&a=<authority>&t=<launch_token?>
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `v` | ✅ | QR 格式版本，当前 1 |
| `s` | ✅ | 信令地址，**完整端点** `wss://host/v1/signal`（不是主机名；见 01 §7） |
| `pt` | ✅ | pair_token：32B 随机 → base64url（无填充）；**单次、TTL 5min** |
| `fp` | ✅ | 插件 **WebRTC DTLS 证书指纹**：`sha-256`、冒号分隔大写十六进制（即 SDP `a=fingerprint` 属性值去掉算法前缀后的部分）。手机据此做 DTLS pin；证书由插件**整证书持久化**、指纹全生命周期稳定（§6）。**是证书哈希而非公钥哈希**。SDP 可能出现多行 `a=fingerprint`，手机 MUST 取 `sha-256` 那一行（§6 归一规则） |
| `a` | ✅ | authority（§1），v1 恒为 `127.0.0.1:13080` |
| `t` | 可选 | DSH launch token。**推荐不写进 QR**：插件 SHOULD 通过 `ctx.connection.authenticatedUrl()` 在内存内取当次进程的 token 并写入 QR（01 §6）。红线：不落盘、不进 `pair.ready`。**可复用性已源码核实（v1.0.4）**：`authorizeIndex` 对 token 只做常量时间比较（`timingSafeEqual`），兑换后不删除、不消费——**同一 token 在进程存活期内可多次交换**（第二台设备扫同一张 QR 也有效）；其可用窗口由 `pt` 的 5min TTL 约束。 DSH 侧调研中"一次性"的准确含义是"URL 交换成功后 303 跳干净地址"，**不是**凭据单次消费 |

## 3. 隧道层

隧道 = 一条 `PeerConnection` + **两条 DataChannel**（均由 offer 方即插件创建）：

| 通道 | 参数 | 承载 |
|---|---|---|
| `data` | `ordered=true`、可靠 | `OPEN` / `DATA` / `FIN` |
| `ctl` | `ordered=false`、可靠 | `PING` / `PONG` / `WINDOW` / `RST` |

> **`FIN` MUST 走 `data` 通道**：它是"本端数据已发完"的顺序标记，跨通道不保证顺序，放在 `ctl` 会导致接收方在最后一个 `DATA` 之前收到 `FIN` 而提前关闭。
> **通道识别（v1.0.4 写死）**：两条通道以 **label**（`"data"` / `"ctl"`）识别，MUST NOT 按创建/到达顺序识别（answerer 侧 `onDataChannel` 的顺序不保证）。收到 label 不符或参数不符的通道 → 视为协议错误，断开并记录。
> 两条通道共享同一条 SCTP 关联，因此**跨通道仍不保证顺序**；拆通道的目的是避开单条有序流上的 **ordering 头阻塞**（丢包重传时，同流后续帧要等待，异流的 `ctl` 帧不必等）。

### 3.1 帧格式

```
+--------+--------+--------+--------------+-----------+-------------+
| ver u8 | type u8| flags u8| stream_id u32| len u32   | payload     |
+--------+--------+--------+--------------+-----------+-------------+
```

- 所有多字节字段为**大端**（BE）；帧头固定 **11 字节**；
- `ver` = 1；非 1 → 立即断开并上报；
- `flags`：**v1 恒为 0**。发送方 MUST 置 0；接收方 MUST 忽略非 0 值（不得据此拒绝帧）；
- `stream_id`：由**手机侧**分配，从 1 递增；**控制帧（`PING`/`PONG`）MUST 用 `stream_id=0`**，接收方 MUST 忽略控制帧中的该字段；
- `len`：payload 字节数，**MUST ≤ 16373**，使总帧长 = 11 + len ≤ **16384（16 KiB）**——与 DataChannel `maxMessageSize` 的语义（整条消息上限）一致；
- 接收方遇到 `len > 16373` 或帧头不完整 → **对该流发 `RST`**（白名单三类之一，§3.3；`stream_id` 不可解析时丢弃整帧并计错）。

### 3.2 帧类型

| type | 值 | payload | 语义 |
|---|---|---|---|
| OPEN | 0x01 | JSON `{"authority":"127.0.0.1:13080"}` | 手机请求新建虚拟 TCP 连接，分配新 stream_id |
| DATA | 0x02 | 原始字节 | 流数据；**同一 stream 内严格保序** |
| FIN | 0x03 | 空 | 半关闭（本端不再发送；对应 TCP FIN） |
| RST | 0x04 | UTF-8 原因串（可选） | 异常重置流，对端 MUST 关闭对应 socket |
| WINDOW | 0x05 | `credit u32` | 流控：接收方通告**新增**信用（见 §3.4） |
| PING | 0x06 | 8B 随机数 | 隧道层保活（与 DSH 的 WS Ping 无关） |
| PONG | 0x07 | 回显随机数 | 对 PING 应答 |

### 3.3 流状态机（必做，实现 MUST 按下表）

| 事件 | 处理 |
|---|---|
| 收到 `FIN` | 对本地 socket 执行**半关闭**（`end()` / `shutdown(SHUT_WR)`），**继续读并继续转发对端数据**（HTTP 请求体以 FIN 结束、响应体随后返回，是合法序列） |
| 同一流再次收到 `FIN` | 忽略（幂等） |
| 本端已发 `FIN` 后收到 `DATA`/`WINDOW` | 正常处理（半关闭仅约束本端发送方向） |
| 对端已 `FIN` 后本端仍收到 `DATA` | 正常转发（半关闭是单向的；此时若本地 socket 已完全关闭，属终态流迟到帧 → **静默忽略**，见下行白名单，不得回 `RST`） |
| 终态/未知流的迟到 `DATA`/`FIN`/`RST` | **静默忽略（不回任何帧）**。**MUST NOT 回 `RST`**——`RST` 走 `ctl`（无序）会先于该流在途的 `DATA`/`FIN`（`data`，有序）到达，若对回 `RST` 会形成两边互相重置的 **RST 风暴**（v1.0.4 修正） |
| 收到 `RST` | 关闭对应流/socket，**一律不回 `RST`**（同上，防风暴） |
| 收到未知 `type` | **静默忽略并计错**，不回帧、不关闭整条隧道 |
| **回 `RST` 的完整白名单（仅以下三类，v1.0.5 写死）** | ① 活跃会话收到**超过并发上限（128）的新 `OPEN`**；② **帧头非法 / `len` 超限**（`len > 16373` 或帧头不完整且 `stream_id` 可解析）；③ **本地 socket 写入错误** |
| 收到 `OPEN` 但 `stream_id` 无效（= 0）或重复（已在流表中，无论该流活跃或已终结） | **静默忽略并计错，不回 `RST`**（该判定**先于白名单①**：id 无效/重复时无论是否超限一律静默）——一个隧道纪元内 `stream_id` 由手机侧从 1 严格递增、不复用（重建后两端已丢弃全部旧流状态并从 1 重启），重放只能源于手机侧实现错误；回 `RST` 会误杀仍在工作的既有流（v1.0.5 补齐第四轮遗留的"OPEN 复用 `stream_id`"待补项） |
| 本地 socket 正常关闭 | 发 `FIN` |
| 本地 socket 写入错误 | 发 `RST` |

### 3.4 流控与队列约束

1. **每条 TCP 连接 = 一个 stream_id**，由手机侧分配；
2. **每隧道并发 stream 上限 = 128**。超出 → 对新 `OPEN` 回 `RST`。接收方内存上界由此可推导：128 × 256 KiB + 8 MiB + socket 缓冲；
3. **WebSocket 独占一条流**：`/api/remote.mux` 的升级请求与其后的全部帧 MUST 在同一条流内（DSH 心跳 2000ms，连续 2 次未回 Pong 即 `terminate()`；二进制帧 → `close(1003)`——隧道只须原样透传字节）；
4. 分片：按 **≤16 KiB** 切 `DATA` 帧（即 `len ≤ 16373`）；接收侧直接写入本地 socket，不缓存整条消息；
5. **信用**：
   - 每流**每方向**初始信用 **256 KiB**；
   - `WINDOW.credit` MUST = **自上次 `WINDOW` 以来，本流本方向已成功写入本地 socket 的累计字节数**（增量，不是余额，也不是固定 64 KiB）；
   - 累计 ≥ 64 KiB 即 MUST 发送一个 `WINDOW`；流关闭前 MUST 把已写入字节数补齐通告；
   - 发送方信用为 0 即 MUST 暂停读本地 socket；
6. **"在途"的定义（写死，避免歧义）**：
   - **在途** = 已交给 `send()` 但**尚未被对端 `WINDOW` 确认**的字节数 —— **包含本地未发送队列**。全局在途 MUST ≤ **8 MiB**；
7. **未发送队列约束（本项是为控制帧延迟服务的关键约束）**：
   - **未发送队列** = `bufferedAmount`（已交给 `send()`、SCTP 尚未发出的字节）；
   - 发送方 MUST 限制：**单流 ≤ 256 KiB，全局合计 ≤ 512 KiB**；达到上限即暂停读本地 socket，直到降到阈值以下（建议用 `bufferedAmountLowThreshold` 驱动恢复）；
   - **理由**：控制帧与 `DATA` 共享同一条 SCTP 关联，队首积压会同时饿死隧道自身的保活帧**与内层 mux 的 PONG**。此上限把控制帧的排队等待限制在 `512 KiB ÷ 链路速率`（2 Mbit/s 下约 2s，仍低于 DSH 侧约 6s 的 mux 容忍窗口）。**它不限制吞吐**（队列随链路速率排空后可继续入队）。
8. 关闭：socket 正常关闭发 `FIN`；`DataChannel` 关闭等价于所有流 `RST`。

### 3.5 保活与隧道重建（本流程在本文内完整定义，文中"方案 B"即指本节）

**双触发器，任一满足即销毁整条 `PeerConnection` 并重建**（不做流内恢复）：

| 触发器 | 条件 | 说明 |
|---|---|---|
| **主触发** | `connectionState` 或 `iceConnectionState` ∈ {`disconnected`, `failed`} | 语义正确、零额外流量。**实测时机待 W1 确认**（`failed` 受 RFC 7675 consent 约束，约 ≤30s；`disconnected` 更早但实现相关）。契约表述为"**45s → 约 ≤30s（实现相关）**" |
| **兜底** | **15s** 未收到任何帧（两端每 **5s** 互发 `PING`） | 15s = 3×5s，避免空载隧道被误判；成本约 +2 MB/天，不构成决策依据 |

**重建规则（全部写死，不留空白）**：

1. **发起方恒为插件**（契约 §4.1 已定插件是 offer 方）→ 重建 = 插件发**新的** `punch.offer`；手机只应答；
2. `punch.request` 的语义是「**请给我一次 offer**」，**不是**"由手机发起"；
3. **§4.1 的 2s 最小间隔只约束插件「自发」重发**；由 `punch.request` 触发的 `punch.offer` **不受该窗口约束**；
4. **`stream_id` 空间在重建后从 1 重启**；两端 MUST 丢弃全部旧流状态（等价于"隧道纪元重置"，无需额外字段）；
5. 重建**不需要**重新配对、不需要新的 `pair.ok`；若此时 TURN 凭证已过期，插件 MUST 先 `relay.request` 取新凭证再 gather（§5）；
6. 重建期间手机侧已有的本地 socket 全部断开（方案 B 的代价，属预期）。

## 4. 信令协议（WSS，JSON 文本帧，一帧一消息）

端点：`wss://<host>/v1/signal`（双方同一端点，角色在 `hello` 中声明）。
心跳为应用层 `ping`/`pong`，**客户端 MUST 每 25s 发一次**；服务端 **60s** 未收到任何帧判离线。
**`t` 是封闭集合**：不在下表的消息类型一律以 `error` 拒绝并关闭连接；**不得**实现任何"通用转发"类型（presence-only 的架构保证依赖这一点）。

### 4.1 消息总表

| t | 方向 | 载荷字段 | 说明 |
|---|---|---|---|
| `hello` | 双→Bridge | `role:"agent"\|"app"`, `pub`(SPKI DER → base64url), `boot_id`(agent 必填), `ts`, `nonce`, `sig`, `proto_ver` | 见 §4.2 的**规范化序列化**。Bridge MUST 校验：时间窗 ±60s、nonce 去重（窗口 MUST ≥ 120s）、`proto_ver` 严格等于 `"1.0.5"`。以 `sha256(pub)` 为设备标识绑定连接：agent 侧记作 **`agent_id`**，app 侧记作 **`phone_id`**（同构，均为身份公钥哈希）。**MUST 在 10s 内收到合法 `hello`，否则关闭连接** |
| `hello.ok` | Bridge→双 | `pair:{pair_id,phone_id,agent_id}\|null`, `peer_online:bool`, `ts` | `pair` 非空 = 免扫码重连成功；`peer_online` 为对端**初始**在线状态 |
| `ping`/`pong` | 双向 | — | 心跳（应用层） |
| `pair.ready` | agent→Bridge | `ptok_hash`(sha256(pair_token) 的 base64url), `ttl` | 插件出 QR 前注册 token；Bridge 只存 hash |
| `pair.ready.ok` | Bridge→agent | `ts` | 注册确认。**没有它，插件 MUST NOT 出 QR**（否则用户扫到的可能是一张绑不上、且只报 `PAIR_NOT_FOUND` 的坏 QR） |
| `pair.bind` | app→Bridge | `ptok` | 扫码后绑定；身份已由 `hello` 确立，不重复携带密钥材料 |
| `pair.ok` | Bridge→双 | `pair_id`, `agent_id`, `turn:{uris[],username,credential,ttl}` | **凭证同时发给两端**。`agent_id` = `sha256(pub)`，**仅供显示/日志，不参与任何 pin 或安全校验**（对端身份校验完全由 §6 的 SDP pin 承担） |
| `presence` | Bridge→双 | `peer_online:bool` | 对端在线状态**变化**推送（初始值随 `hello.ok` 下发） |
| `presence.get` | 双→Bridge | — | 主动查询，Bridge 以 `presence` 应答（推送决策前 MUST 调用，防竞态） |
| `punch.request` | app→agent（经 Bridge） | `pair_id` | "请给我一次 offer"。**agent 不在线（宽限期内）→ Bridge MUST 回 `error PEER_OFFLINE`，不得静默丢弃** |
| `punch.offer` | agent→app（经 Bridge） | `pair_id`, `sdp` | **非 trickle** 完整 SDP（host+srflx+relay 候选**一次收齐**，含 `a=fingerprint`）。插件可主动重发（§3.5）；**自发重发之间 MUST ≥2s**，且同一 pair 同时只允许一个进行中的 offer/answer。**手机离线时 Bridge 不转发，向插件回 `error PEER_OFFLINE`** |
| `punch.answer` | app→agent（经 Bridge） | `pair_id`, `sdp` | 完整 SDP answer |
| `relay.request` | 双→Bridge | — | 请求 TURN 凭证。**任何一次新 gather 之前**（首次、免扫码重连、网络切换、隧道重建），若本地无凭证或剩余 TTL 低于阈值，MUST 先请求（§5） |
| `relay.alloc` | Bridge→双 | `turn:{uris[],username,credential,ttl}` | `relay.request` 的应答（字段与 `pair.ok` 的 `turn` 完全同构，只写一次定义） |
| `bye` | 双向 | `reason:"user"\|"shutdown"` | **显式撤销**：Bridge 收到后 ①**立即销毁 pair** ②向发送方回 **`bye.ok`** ③向对端**转发** `bye`。发送方收到 `bye.ok`（或超时 2s）后 MUST 销毁本地 `PeerConnection`/`DataChannel` 并清本地配对信息。**对端离线时 Bridge 只回 `bye.ok`，不转发**——对端下次 `hello` 得 `hello.ok{pair:null}` |
| `bye.ok` | Bridge→单 | `ts` | `bye` 的确认（见上） |
| `error` | Bridge→单 | `code`, `msg` | 错误（§4.5；`code` 为字符串，与 WS 升级阶段的 HTTP 状态码无关） |

### 4.2 `hello` 的规范化序列化（跨 JS / Go / Kotlin 必须逐字节一致）

定义不写死会导致"三端单测各自全绿、联调时 100% 验签失败"。以下为**规范性**条款：

| 项 | 规范 |
|---|---|
| `ts` | **epoch 秒**（不是毫秒），JSON number，十进制整数，无小数、无前导零、无指数 |
| 被签名串 | UTF-8 字节：`"hello\|" + String(ts) + "\|" + nonce`，其中 `String(ts)` 为 `ts` 的十进制 ASCII 表示 |
| `nonce` | **32 字节随机 → base64url（无填充）**；每次 `hello` MUST 新生成 |
| `sig` | 设备私钥对上述 UTF-8 字节做 **ECDSA P-256 / SHA-256**，签名编码为 **DER（ASN.1 SEQUENCE(r,s)）→ base64url**。**不得**输出 IEEE P1363(r‖s) 定长形式；若实现内部产出该形式，MUST 转为 DER |
| `pub` | SPKI DER → base64url |
| `proto_ver` | 字符串，Phase 1 恒为 `"1.0.5"` |

> 三端 MUST 共用 `remotedsh-contract` 里同一份 `hello` 签名测试向量（固定密钥、`ts`、`nonce` → 期望签名与期望字节串），作为 CI 门禁。

### 4.3 pair 生命周期

**判定原则**：pair 的存亡取决于「**同一台 PC 上的同一个 DSH 进程是否还在**」，而不是「TCP 连接是否还在」。

**`boot_id`**：插件在每个 **DSH 进程**启动时生成一个随机标识，随 `hello` 上报，Bridge 与 pair 一同保存。它 MUST 是**进程级**（例如 `process.pid` + 进程启动时刻，或首次生成后挂到 `globalThis`），**不得**在 `apply()` 中随插件实例生成——否则 web profile 的 `patchReload: live` 热重载会被误判为"DSH 重启"。`boot_id` **不是身份**，不参与验签，不入 QR。

**pair 记录 MUST 保存 `phone_id` 与 `agent_id`（而不是连接对象）**，投递时按 id 解析**当前**连接；连接已被替换则发给新连接。

**pair 销毁共五个触发条件，且每一个都 MUST 向仍在线的对端主动推送**（不得依赖"对端下次 `hello`"——对端的 WSS 往往还活着，因为它不是消失的那一端）：

| # | 触发条件 | 对端收到的推送 | 对端文案 |
|---|---|---|---|
| ① | 任一端发 `bye` | 转发的 `bye`（发送方收 `bye.ok`） | "对端已主动解除配对，请重新扫码" |
| ② | 插件以同一 `agent_id` 重连但 `boot_id` **不同** | `error AGENT_RESTARTED` | "电脑上的 DSH 已重启，请重新扫码" |
| ③ | 插件断开后**宽限期 T = 24 小时**内未以相同 `boot_id` 重连 | `error PAIR_EXPIRED` | "PC 离线超过 24 小时，配对已失效，请重新扫码" |
| ④ | 新手机对同一 agent `pair.bind` | 旧手机收 `error PAIR_REPLACED` | "已在另一台手机完成配对" |
| ⑤ | **手机对另一 agent `pair.bind`（一手机只连一台电脑，v1.0.5 写死）** | **旧 agent** 收 `error PAIR_REPLACED` | "该手机已在另一台电脑完成配对" |

**配对数约束（v1.0.5）**：**每 agent 至多 1 个 pair，每 phone 至多 1 个 pair**——产品约束为**一台手机只配一台电脑**；手机扫新电脑的 QR 即自动销毁旧 pair（条件⑤），旧电脑侧收到 `PAIR_REPLACED` 后拆毁既有隧道并恢复未配对状态（重新注册 pair_token、恢复 QR 轮印，§4.4/§4.5）。

**T = 24 小时的产品含义（必须写清，否则会被当成 bug）**：条件 ①②承担全部语义判断（正常关闭、DSH 重启都立即销毁），因此 **T 纯粹是内存上界**——它决定的是「**PC 侧离线多久以内，手机不必重新扫码**」。24 小时意味着笔记本合盖、断网、切 VPN 在 24 小时内都不需要重新扫码；**PC 侧离线超过 T 就必须重新扫码**，与 DSH 是否重启无关。

**宽限期计时器规则**：每次 agent 连接断开即**重新起算**，同 `boot_id` 重连即**取消**；不得"沿用"上一轮剩余时间。

**明确禁止在"连接关闭回调"里销毁 pair**：插件重连时 Bridge 会踢掉旧连接，若旧连接的 close 回调触发销毁，会把新连接刚挂载的 pair 一并删掉。销毁只由上述五个条件触发。

**手机侧断开不销毁 pair**：手机可长期离线，回来凭 `hello.ok{pair}` 免扫码恢复。

```
首次配对：插件 hello(boot_id) → pair.ready → pair.ready.ok → 出 QR
          手机扫码 hello → pair.bind(ptok) → Bridge 校验 → pair.ok（含 TURN 凭证）
          → 手机 punch.request → 插件 punch.offer → 手机 punch.answer → ICE 并行探测
手机重启：手机 hello → hello.ok{pair 非空, peer_online}
          → 若凭证已过期则 relay.request → punch.request → offer/answer → 免扫码重建
手机断开：不影响 pair；期间广播 presence{peer_online:false}
插件侧抖动（boot_id 相同）：pair 保留 → presence{peer_online:false} → 插件重连并重新挂载原 pair
          → 插件主动重发 punch.offer → 手机应答 → 快速重建（<5s 目标）
DSH 重启（boot_id 不同）：销毁 → 手机收 error AGENT_RESTARTED → 提示重新扫码
宽限期 T=24h 超时：销毁、ptok_hash 清除 → 手机收 error PAIR_EXPIRED → 提示重新扫码
Bridge 进程重启：内存清空 → 两端重连 → 手机收 hello.ok{pair:null} → 提示重新扫码
          （这是状态丢失，不是销毁触发条件；属预期行为）
新设备替换：手机 B 对同一 agent pair.bind → 旧 pair 销毁 → 旧手机收 error PAIR_REPLACED
          （每 agent 至多 1 个 pair）
手机换绑：已配对的手机对另一 agent pair.bind → 旧 pair 销毁 → 旧 agent 收 error PAIR_REPLACED
          （每 phone 至多 1 个 pair；一台手机只连一台电脑）
隧道重建：见 §3.5（不涉及 pair 与配对）
打洞：单阶段 ICE——首次收集即含 TURN 候选，P2P/TURN 由 ICE 并行探测自动择路，无"失败后二次切换"
```

### 4.4 配对 token 与 QR 的有效期

- `ptok_hash` 注册后 **TTL 5min**；同一 agent 再次注册 MUST 作废旧 hash；
- **pair 销毁后，销毁前生成的任何未过期 QR MUST 不可再绑定**（Bridge 在销毁时清除该 agent 的 `ptok_hash`）；
- 插件在 token 过期前 SHOULD 重新注册并重印 QR；**`pair` 存续期间（已收 `pair.ok` 且未被条件①–⑤销毁）MUST NOT 重印**；pair 销毁后 agent 恢复轮印——触发信号：条件①对端 `bye`（或本端 `bye` 收到 `bye.ok`）、条件⑤ `PAIR_REPLACED`、重连后 `hello.ok{pair:null}`。

### 4.5 错误码

`code` 为**字符串**，属消息级应用层错误——与 WS 升级阶段可能出现的 HTTP 状态码无关：

| code | 含义 | 客户端动作 |
|---|---|---|
| `AUTH_FAILED` | 验签失败 / token 无效 | 断开；App 提示重新扫码 |
| `PROTO_VER_UNSUPPORTED` | `proto_ver` 不受支持 | **提示升级客户端；MUST NOT 重试、MUST NOT 提示重新扫码**（重扫码无法解决版本偏差） |
| `PAIR_NOT_FOUND` | pair 不存在 | App 提示重新扫码 |
| `AGENT_RESTARTED` | 对端 DSH 已重启（`boot_id` 变化） | 明确提示"电脑上的 DSH 已重启，请重新扫码" |
| `PAIR_EXPIRED` | 宽限期超时（PC 侧离线超过 T） | 明确提示"PC 离线超过 24 小时，配对已失效，请重新扫码" |
| `PEER_OFFLINE` | 对端当前不在线（宽限期内） | 保持连接，等 `presence` 恢复后重试 `punch.request` |
| `PAIR_REPLACED` | pair 已被新设备替换（④新手机挤掉旧手机 / ⑤手机换绑另一台电脑） | **手机侧按方向区分（v1.0.5 写死）**：**被动方**（被新手机挤掉，本地无更新的绑定）→ 清本地配对信息；提示重新扫码。**主动换绑方**（本端刚扫新 QR 完成换绑、本地已绑定更新的 pair——`PAIR_REPLACED` 可能由本端自己的 `pair.bind` 触发、先于新 `pair.ok` 到达）→ **MUST 忽略**：不清新配对、不提示，以本地最新绑定为准。**插件侧**（条件⑤收件方，该手机已换绑他机）→ 拆毁现有 `PeerConnection`/两条 `DataChannel` 与全部 stream socket，恢复未配对状态：生成新 `pair_token` → `pair.ready` → 恢复 QR 轮印（§4.4 的"存续期不重印"随 pair 销毁解除；若插件离线后重连，则由 `hello.ok{pair:null}` 触发同一流程） |
| `PAIR_LIMIT` | **实例级** pair 已达上限（256） | **提示"服务繁忙"，不自动重试**（超限直接拒绝访问，用户 2026-09-13 决策；不做 LRU 淘汰） |
| `RATE_LIMITED` | 限流 | 指数退避 |
| `INTERNAL` | 服务端内部 | 指数退避重连 |

> `pair_id` 一致性断言失败（对端转发的 `pair_id` 与连接绑定的 pair 不符）→ 回 `error PAIR_NOT_FOUND` 并记录告警；**不得**跨 pair 路由。

## 5. TURN 凭证方案（coturn REST API 机制）

- coturn 配置 `use-auth-secret` + `static-auth-secret=<S>` + **`lt-cred-mech`**（coturn 文档："WebRTC relaying will not work with anonymous access"）；`S` 仅存在于 Bridge 与 coturn 部署环境，**不下发**；
- Bridge 为每对签发：`username = "<expire_epoch>:<pair_id>"`、`credential = base64(HMAC-SHA1(S, username))`、**TTL 3600s**；**两端拿到的是同一个 coturn 用户名**；
- `uris`：`stun:<host>:3478`、`turn:<host>:3478?transport=udp`、**`turn:<host>:3478?transport=tcp`**（UDP 被封网络的兜底；coturn 只需不设 `no-tcp`，无需证书）。5349/`turns:` 列为后续变更；
- **凭证 TTL 只约束「新建 allocation」**。coturn 的 allocation 由客户端 Refresh 维持——官方原文：*"the original password becomes the session parameter and is never expiring. So, if the session is properly maintained, it may go forever"*；**续句同样重要**：*"while the session is valid and unexpired … Once the session got disconnected, the client will have to use the new password to re-connect"*（默认 `max-allocate-lifetime` 3600s）。因此：
  - 已建立的隧道**不需要**"到期前续期"来维持；
  - `relay.request` / `relay.alloc` 的真实用途是**为将要发生的新 gather 准备有效凭证**——**任何一端在发起新的 gather（含免扫码重连、网络切换、隧道重建）之前，若本地无凭证或剩余 TTL < 300s（统一阈值，v1.0.4 写死），MUST 先 `relay.request` 取新凭证**，否则 offer/answer 会**静默缺少 relay 候选**（对称 NAT 下失败且不报错）；
  - **禁止**把"续期"实现成"重新 allocate"——那会掐断正在工作的隧道；
- 带宽限制由 coturn **`max-bps`（单会话）** 与 **`bps-capacity`（整机合计，非单用户）** 执行；`user-quota` 是**并发分配数**（因两端用同一用户名，若设置 MUST ≥2）；按天流量配额（目标 ≤200MB/天/对）由部署侧用量监控告警执行——coturn 无原生按天配额。

## 6. 身份与 pin 规则

| 主体 | 密钥/证书 | 存储 | 用途 |
|---|---|---|---|
| 插件（PC）身份密钥 | P-256，长期 | 首次生成后持久化（`$DSH_HOME` 下文件；见 01 §4.1） | `hello` 签名；`agent_id = sha256(pub)` |
| 插件（PC）DTLS 证书 | P-256 证书，**首次生成后整证书持久化（证书+私钥一起存，不重新派生）** | 与身份密钥一同存放 | WebRTC DTLS 证书；SDP `a=fingerprint` 全生命周期稳定 → QR `fp` 即此证书的 **sha-256** 指纹。插件 SHOULD 用 werift `RTCCertificate.getFingerprints()` 的输出生成 `fp`，避免自算格式偏差 |
| 手机设备身份 | P-256，长期 | **Android Keystore**（不可导出） | `hello` 签名；`phone_id = sha256(pub)` |
| 手机 DTLS | P-256 证书 PEM | `RtcCertificatePem` 生成一次，本地加密存放 | 证书指纹稳定（供插件未来 pin；v1 插件侧不强制 pin 手机） |

### 6.1 pin 校验点（红线）

**手机 MUST 在每一次 `setRemoteDescription` 之前执行**（不只是首次配对——插件可在任意时刻主动重发 `punch.offer`）：

1. 从 offer SDP 中取 `a=fingerprint` 行；**多行时 MUST 取 `hash-func` 归一后等于 `sha-256` 的那一行**（RFC 8122 §5.1 允许多行；取到 `sha-1` 行会导致永不匹配）。行可位于 session 级或 media 级，冲突时以 media 级为准；
2. 对该行取值执行**强制归一**（同一个确定性算法，不得"可选"）：
   > **剥掉 `hash-func` 前缀 → 删除全部冒号与空白 → ASCII 小写 → 按字节比较。**
3. 与本地持久化的 `fp` 比较（不是与"内存里的 QR 内容"比较——**手机 MUST 把 `fp` 与配对信息一起持久化**，否则 App 重启后的免扫码重连将无法 pin）；
4. **不一致 → 立即中止，MUST NOT 继续 `setRemoteDescription`**；
5. **若 offer 中不存在 `sha-256` 行 → MUST 立即中止（fail-closed）**，不得"找不到就不比"。

> `a=fingerprint` 是**整张证书**的哈希（RFC 8122 §5），不是公钥哈希。这也是插件必须**持久化证书本身**而非每次从密钥重新派生的原因：重新派生的证书序列号/有效期不同，指纹会变。

### 6.2 不参与安全校验的字段（避免再次误用）

`agent_id` / `phone_id` 是**设备标识**（Bridge 用它做连接绑定与重启判定，因此**必须存进 pair 记录**），但**不参与 pin、不参与身份校验**；`boot_id` 仅供 Bridge 判定进程身份。三者都不构成身份校验。
