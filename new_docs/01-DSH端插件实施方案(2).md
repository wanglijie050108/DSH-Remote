# 01 · DSH 端插件实施方案（`dsh-mobile-link`）

> 版本：v1.2 · 2026-09-12 · 所属：`../implementation/README.md` 第一阶段
> 设计依据：`../../remote-link/remote-link-design-v0.4.md`（§3.3 插件形态、§4 链路、§5 配对）
> 契约：`./00-接口契约.md` **v1.0.5**（下称"契约"）

## 1. 预期目标

交付一个 DSH bundle **`dsh-mobile-link`**，随 DSH 进程启停，使 Android 手机（或 fake-phone）能够：

1. 经 WebRTC DataChannel（P2P 或 TURN）与本插件建立**端到端加密隧道**；
2. 通过隧道把 `127.0.0.1:3080` 的 DSH 完整 HTTP + WebSocket 面呈现给手机（L4 字节泵，不做任何 HTTP 语义处理）；
3. 每次 DSH 进程启动生成配对 QR（含 pair_token、插件证书指纹，以及本进程的 launch token）；
4. 与 Bridge 保持信令长连接（presence、候选/SDP 撮合、TURN 凭证接收）。

**DoD（本部分验收）**：

- [ ] W2：fake-phone → 插件 → 真实 DSH 全链路出画面（全 TURN 路径）；
- [ ] E1：**>1MiB 的响应**经隧道 sha256 与直连一致；HTTP/1.1 keep-alive 无异常。靶子用组合 URL `/plugins/??<id1>/client.js,<id2>/client.js,…`（单个 `/plugins/<id>/client.js` 本机最大仅 **620160 B = 0.5914 MiB**；**48 个合计 3.62 MiB**，组合 URL 的 id 部分约 1.7 KB，低于 `dsh-client-modules` 的 3 KiB 分段阈值）；**两腿 MUST 固定同一个 `Accept-Encoding`**（web profile 已开 `compression: gzip`，协商不同会假失败）；
- [ ] E2：WS（`/api/remote.mux`）30 分钟连续收发不被 DSH `terminate()`，含人为抖动 1s；
- [ ] E3：`Host`/`Origin`/`Cookie`/`Sec-Fetch-Site` 原样到达 DSH。**改 Host 的断言必须指定路径**：仅 `/api*` 返回 403（围栏 `isTrustedApiRequest` 只由 `/api` 前缀路由与 `/api/remote.mux` 升级调用）；`GET /` 返回 **401**（`authorizeIndex`）；`/plugins/*` 与 dist 静态资源**公开**（会返回 200）；
- [ ] DSH 正常启停 10 次，插件**每次都装配成功**（CI 断言，配 `tools/fake-bridge` 后追加"并上线"断言）；
- [ ] **E10（pair 生命周期与热重载）**：①网络抖动（`boot_id` 相同）→ 免扫码自动重建；②DSH 重启（`boot_id` 变化）→ 手机收 `AGENT_RESTARTED` 且必须重新扫码；③正常关闭 → `bye` → 立即销毁；④宽限期 T=24h 超时 → 清理；⑤**踢旧连接不得误删新挂载的 pair**；⑥**live 热重载后插件 MUST 在 <6s 内重连成功 ⇒ 手机侧无感**（6s = DSH mux 容错 2s×2；这是 §2.2 不发 `bye` 的验收条件）；⑦**手机对另一 agent `pair.bind`（换绑，契约 §4.3 条件⑤）→ 本插件收 `PAIR_REPLACED` → 拆毁隧道并恢复 QR 轮印（§4.4）**；
- [ ] 无崩溃残留、无端口泄漏；故障注入符合 §2.1 失败模型。

**非目标（本部分）**：HTTP 解析/L7 逻辑、审批应答逻辑（官方前端负责）、推送（N3）、设备表/持久化配对、隧道层去重。

## 2. 形态与生命周期

- 包名 `dsh-mobile-link`，bundle 形态挂入 `dsh --profile web`：

```jsonc
// package.json（节选）
{
  "name": "dsh-mobile-link",
  "type": "module",
  "main": "./lib/index.js",
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
}
```

> **不要加 `exports` 映射。** `dsh-app-boot` 的 `resolveBundleDir` / `packageDirFromAnchor` 是**文件系统遍历**（`createRequire(anchor).resolve.paths()` + `existsSync(join(candidate,"package.json"))`），其注释明确写着 *"Resolution does not require the package to export `./package.json`"*，且 manifest 与 patch 都用绝对路径 `readFileSync` 读盘、不经 exports 映射。若仍然要写 `exports`，则 `"."` 与 `main` **至少其一**必须存在；`./cordis.patch.yml` 与 `./package.json` 两条 subpath **冗余且可安全删除**（v1.1 曾误写为必需）。

```yaml
# cordis.patch.yml
- insert:
    - id: mobile-link
      name: 'dsh-mobile-link'
```

**安装方式**（README 必须写）：

```
dsh plugin --profile web add dsh-mobile-link
```

该命令把参数转发给 profile 目录下的 pnpm，然后由 `reconcilePlugins` 把包名追加进 `$DSH_HOME/profiles/web/package.json` 的 `dsh.profile.bundles`——**不是**手改 `cordis.patch.yml`。前置条件：**PATH 上必须有 pnpm**，否则返回 127 并提示。

```js
// lib/index.js
export const name = 'dsh-mobile-link'
export const inject = ['webServer', 'connection']
// webServer  → 取真实 DSH 端口（ctx.webServer.port）
// connection → 取本进程 launch token（ctx.connection.authenticatedUrl()，§6）
// N3 推送时追加 'approval'
export function apply(ctx) {
  // 启动成功是硬性前提（§2.1）：
  // import 期零 IO/零网络；apply() 只做本地装配（读配置 → 载入密钥/证书 → 起组件）
  // 装配失败 → 快速失败、报错明确（连带 DSH 启动失败，属已接受耦合）
  // 运行期故障（Bridge 不可达等）→ 退避重试 + 状态输出，不阻断启动
}
```

> **`inject` 的代价必须写明**：本插件因此**只能在同时具备 `webServer` 与 `connection` 的组合中使用**（web profile 两行都在）。若挂到缺任一服务的组合里，该行会进入 FIBER_PENDING，`dsh-app-boot` 的 `assertEntriesActivated` 把 pending 计为失败 → **DSH 启动失败**。这是为换取"真实端口 + 程序化 token"而付的代价，已接受。

### 2.1 失败模型（启动成功是硬性前提，不是"失败也不影响"）

bundle 装配成功是本功能运行的**必要条件**；装配失败会连带 DSH 启动失败——这是 v0.4 §3.3 已接受的耦合，**不设计"静默降级"**。按阶段划分：

| 阶段 | 故障 | 策略 |
|---|---|---|
| import | — | **零 IO、零网络**：模块顶层只做纯定义，依赖在 package.json 锁死版本 |
| apply | 配置缺失 / 非法（`DSML_SIGNAL_URL` 未设或形态错误、`DSML_AUTHORITY` ≠ 契约固定值） | **fail-fast**：抛出并打印缺失项与正确形态，终止装配 |
| apply | 密钥/证书文件损坏 | **fail-fast**：报错并给出恢复方式（删除 `$DSH_HOME/mobile-link/identity.json` 重启 → 自动生成新钥；**所有手机需重新扫码**） |
| apply | 依赖不可用（werift 装载失败等） | fail-fast（W1 已验证可用性 + 锁版本） |
| 运行期 | Bridge 不可达 / WSS 断开 | **不阻断启动**：指数退避重连（500ms→30s），控制台持续输出连接状态 |
| 运行期 | DSH 端口拒绝、TURN 不可用、punch 失败 | 重试 + 状态输出，恢复后自动上线 |

**门禁**：CI 断言"配置正确 → 装配成功"必须 100%；故障注入按上表验证两类行为。

> **fail-fast 必须自带自救指引**：DSH 会因本插件装配失败而拒绝启动，用户此时进不了 UI。每条 fail-fast 报错 MUST 额外打印：
>
> ```
> 修复方式：在 $DSH_HOME/profiles/web/cordis.patch.yml 加入
>   - id: mobile-link
>     disabled: true
> 后重启 dsh；修好配置再去掉这段。
> ```

### 2.2 dispose 与清理

插件持有：到 Bridge 的 WebSocket、`PeerConnection`、**两条 `DataChannel`**、**每条 stream 一个 `net.Socket`**。以下事件都会触发 Cordis fiber dispose：DSH 退出、用户把该行 `disabled`、以及 **web profile 的 `patchReload: live` 热重载**（`PROFILE_TEMPLATES.web.patchReload = "live"`）。

**关键区分（v1.1 的错误已修正）**：

> **"fiber dispose" ≠ "DSH 进程退出"。** 热重载只 dispose 本插件的 fiber，进程仍在。因此：

| 事件 | 是否发 `bye` | 理由 |
|---|---|---|
| **DSH 进程退出**（SIGINT/SIGTERM → root context 异步 drain） | **发**（尽力而为） | 让"用户正常关闭 DSH"的撤销**立即**生效，而不是等 24h 宽限期 |
| **fiber dispose（热重载 / 该行被 disabled）** | **不发** | 发 `bye` = 立即销毁 pair = 逼用户重新扫码——**这正是 `boot_id` 要防的事**。不发则靠 `boot_id` 在宽限内恢复 |

清理顺序（全部通过 `ctx.effect()` 登记 disposer）：

1. **仅当进程退出时**：向 Bridge 发 `bye{reason:"shutdown"}`，**尽量等待 `bye.ok`（上限 2s）**，并 `await` 发送完成（走 root context 的异步 drain 比 `process.on('exit')` 的同步写可靠）；**仍属"尽力而为"** —— 硬杀/崩溃/断电必然丢失，由 T=24h 宽限期兜底，**不得写成硬保证**；
2. 关闭全部 `net.Socket` 与 stream；
3. 关闭两条 `DataChannel` 与 `PeerConnection`；
4. 关闭到 Bridge 的 WebSocket；
5. 清除定时器（重连退避、保活 PING、宽限于本插件无）。

> **"进程退出 vs 热重载"如何判定 —— 本版不明文指定实现，交 W1/E10 定案。** 两个候选：
> ① 在 disposer 中检查 root fiber 是否已进入 disposing 状态（root 仍在活动 ⇒ 只是本行被重载 ⇒ 不发）；
> ② 由 SIGINT/SIGTERM 监听器置标志（注意 DSH 自身的处理器**先注册先执行**，不能只依赖标志，需配合有界等待）。
> **两种候选的失败方向都是"漏发 `bye`"（安全侧）**，因为漏发的代价只是"等 T 兜底"，而误发的代价是"逼用户重新扫码"。E10 断言 ⑥ 是本条的验收条件。

**E10 断言 ⑥ 是这条的验收条件**：热重载后插件 MUST 在 6s 内重连成功（同 `boot_id`），否则手机会看到 mux WS 重建。

### 2.3 boot_id（进程级，必须）

- **必须进程级**：`process.pid + 进程启动时刻`，或首次生成后挂到 `globalThis`；**不得**在 `apply()` 里随插件实例生成——否则一次 live 热重载就会被判成"DSH 重启"；
- 不是身份，不参与验签，不进 QR。

## 3. 技术选型

| 项 | 选型 | 理由 / 备选 |
|---|---|---|
| WebRTC | **werift**（纯 TypeScript） | 避免原生模块在**运行期**崩溃波及 DSH 进程 |
| WS 客户端 | `ws` | 标准选择 |
| QR | `qrcode`（terminal 输出） | 插件无 UI |
| 密钥/证书 | Node crypto（P-256） | 生成身份密钥 + **一次性生成 DTLS 证书**并持久化 |

> **W1 第一件事：werift 与 org.webrtc（Android）互通性 PoC。** 判据三条：① 指纹 pin 通过；② 非 trickle offer 含 host+srflx+relay 三类候选；③ 单条有序 DataChannel 双向 16 KiB 帧无误。
> **已核实（可排除的风险，2026-09-13 实测补记，changelog 004/009）**：werift 0.24.4 的 `RTCCertificate(privateKeyPem, certPem, signatureHash)` + `RTCConfiguration.certificates` + `PeerConfig.dtls.keys` 都存在 → **"整证书持久化 → 指纹稳定"可实现**；`getFingerprints()` 返回 `{algorithm,value}[]`，可直接用于生成 QR `fp`。**★ 第三参必须是 `{hash, signature}` 枚举对象**（`{hash: HashAlgorithm.sha256_4, signature: SignatureAlgorithm.ecdsa_3}`，即 4/3）：传字符串 `'sha-256'` 时构造器不报错、但 **DTLS 握手必败**（werift↔werift 同样失败，报错点与原因无关）。事件 API 用 DOM 风格属性（`pc.ondatachannel`/`ch.onopen`/`ch.onmessage`）或 `Event.subscribe()`，把函数直接赋给 Event 属性会运行时报错。非 trickle（`setLocalDescription` 返回后 SDP 已含全部候选）、双 DataChannel（label `data`/`ctl`）、16373B 边界帧均已在 werift↔werift 回环验证通过（`remotedsh-contract/scripts/poc-werift-loopback.mjs`，可复跑）。
> **仍需实测**：① 注入持久化证书后与 **org.webrtc（真机）** 的握手/指纹协商是否一致（werift↔werift 已通，此条仅剩 Android 侧）；② `disconnected`/`failed` 的**触发时机**（决定 §3.5 主触发能否单独覆盖前端窗口）；③ `bufferedAmount` 积压实测（决定 §3.4 队列阈值）。

## 4. 模块设计

```
dsh-mobile-link/
├─ lib/index.js          # apply()：最小装配 + dispose 清理（§2.1/§2.2）
├─ lib/config.js         # 环境变量 + ctx.webServer.port 取真实端口（§7）
├─ lib/keys.js           # P-256 身份密钥 + DTLS 证书一次性生成并持久化
├─ lib/rtc.js            # werift PeerConnection + 双 DataChannel + 证书注入 + 重建
├─ lib/tunnel.js         # L4 帧编解码 + 流会话 + 流控 + 队列约束 + 字节泵
├─ lib/pairing.js        # pair_token / QR 渲染（含 launch token 注入）
├─ lib/bridge.js         # WSS 客户端（重连退避、boot_id、消息分发）
└─ lib/approve.js        # N3 预留 stub
```

### 4.1 keys.js — 插件身份与证书

- 首次启动生成 P-256 密钥对并**持久化**：
  - **首选：`$DSH_HOME/mobile-link/identity.json`**（PKCS8 PEM；Windows 下用 ACL 收窄，不要写 `chmod 0600`——该语义在 Windows 不成立）。这与 DSH 自身做法一致（浏览器会话密钥即存于 `$DSH_HOME/.credentials.yaml`）；
  - 可选：DSH storage 域。注意 **`ctx.storage` 是注册表（hub），不是 KV 存储**；写记录必须走 `ctx.storageDomain`（需 `storage`+后端+`storage-domain` 三行齐备、`defineDomain`/`domainTable` + schema；`defineDomain` 支持 `compatibleVersions` 声明相容版本，故"无迁移"成立，但版本相容必须**显式声明**，否则不匹配即拒绝）。对一对密钥而言是重武器，**v1 不用**；
- 同时**一次性生成 WebRTC DTLS 证书**（P-256），**证书与私钥一同持久化——不每次重新派生**（重新派生的序列号/有效期不同，指纹会变）；
- 私钥永不进入日志；QR 的 `fp` **SHOULD 直接取 `RTCCertificate.getFingerprints()` 中 `algorithm` 归一为 `sha-256` 的 `value`**，避免自算 DER 哈希带来的格式偏差（契约 §6）。

### 4.2 tunnel.js — 隧道核心（本插件工作量主体）

- **帧编解码**：按契约 §3.1/§3.2 实现，单测引用 `remotedsh-contract` 共享测试向量。必须落实：`flags` 恒 0、`len ≤ 16373`（总帧 ≤16384）、超限 → `RST`；
- **流状态机**：实现契约 §3.3 那张表。**半关闭是红线**——收到 `FIN` 只做 `socket.end()`，**继续读并继续转发**，否则 HTTP 响应体会被静默截断；
- **StreamSession**：`OPEN` → 校验 `payload.authority == 契约 §1 固定值`（一致性断言）→ `net.connect(<转发目标>)` → 双向泵：
  - 转发目标 = `127.0.0.1` + **`ctx.webServer.port`**（契约 §1）。**禁止使用 `ctx.webServer.host`** —— 该 getter 返回的是**配置值**，可能是 `0.0.0.0`；
  - socket → DATA：按 ≤16 KiB 切帧；**信用为 0 即 `pause()` 读 socket**；
  - **背压（v1.1 的错误已修正）**：werift 的 `RTCDataChannel` 只有推送式 `onMessage` + `send()` + `bufferedAmount` / `bufferedAmountLowThreshold`，**没有"停止读取"的 API**。因此反压不靠"不读"，而靠两条：
    1. **不回 `WINDOW`**（契约 §3.4：信用是接收方唯一能停住对端的手段）；本地 socket 排水完成后按"自上次 WINDOW 以来实际写入的字节数"回填；
    2. **限制本地未发送队列**：单流 `bufferedAmount` ≤ 256 KiB、全局 ≤ 512 KiB；达上限暂停读本地 socket，降到 `bufferedAmountLowThreshold` 以下再恢复；
  - **红线：绝不在 WebRTC 回调线程里阻塞写 socket。** `onMessage` 回调里只做入队，实际写盘/写 socket 在独立协程/任务队列中完成——阻塞回调会拖垮整条 `PeerConnection`；
  - 每写出 ≥64 KiB 回 WINDOW（值为**增量**，不是固定 64 KiB）；
  - 并发 stream 上限 128，超出对新 `OPEN` 回 `RST`；
  - socket close → `FIN`（走 `data` 通道）；write 错误 → `RST`（走 `ctl`）；
- **两条 DataChannel**（offer 方创建）：`data`(`ordered=true`，可靠)承载 `OPEN`/`DATA`/`FIN`；`ctl`(`ordered=false`，可靠)承载 `PING`/`PONG`/`WINDOW`/`RST`。**`FIN` 必须走 `data`**，否则可能在最后一个 `DATA` 之前到达；
- **保活与重建**：按契约 §3.5 —— 主触发 = `connectionState`/`iceConnectionState` ∈ {disconnected, failed}；兜底 = 5s `PING` / 15s 无帧；**发起方恒为插件**（发新的 `punch.offer`）；
- **心跳透明性红线**：插件只搬运字节，绝不吞 DSH 的 2s WS Ping、绝不做 UTF-8 转换（否则触发 DSH `terminate()`/`close(1003)`）。

### 4.3 pairing.js — 配对

- 启动即生成 pair_token（32B 随机 → base64url，内存保存原值，sha256 后经 `pair.ready` 注册，TTL 5min）；
- **必须等到 `pair.ready.ok` 才渲染 QR**（契约 §4.1：否则用户可能扫到一张绑不上的坏 QR，且只报 `PAIR_NOT_FOUND`）；
- **launch token 由程序取得**（§6）：`ctx.connection.authenticatedUrl('http://127.0.0.1:13080/')` 取出 `token` 参数写入 QR `t` 字段——**不需要用户手工拷贝**；
- 渲染：`qrcode` terminal 二维码 + 一行纯文本 URI；token 过期前重新注册并重印 QR；**`pair` 存续期间（收到 `pair.ok` 且未被契约 §4.3 条件①–⑤销毁）MUST NOT 再重印**；pair 销毁后恢复轮印（§4.4）；
- pair_token 用后即弃：收到 `pair.ok` 后从内存删除。

### 4.4 bridge.js — 信令客户端

- 连接 `wss://<DSML_SIGNAL_URL>/v1/signal`（**`DSML_SIGNAL_URL` 是主机名，不是完整端点**，见 §7）；
- `hello{role:"agent", pub, boot_id, ts, nonce, sig, proto_ver}`，**序列化严格按契约 §4.2**（`ts`=epoch 秒十进制、`nonce`=32B→base64url、被签名串 UTF-8、`sig`=ECDSA P-256/SHA-256 **DER**→base64url）。三端共用签名测试向量；
- 断线重连：指数退避 500ms→30s + 抖动。**重连不发新的 `pair.ready`**——只在 `hello.ok{pair:null}` 之后发（否则每次网络抖动都会重印一张 QR）；
- 处理 `PROTO_VER_UNSUPPORTED` → 明确报错退出装配（不重试）；
- 撮合：收到 `punch.request`（或需自发重建）→ 创建 `PeerConnection`：
  - **gather 之前**：若本地无 TURN 凭证或剩余 TTL 低于阈值 → **先 `relay.request`**（契约 §5）；否则 offer 会**静默缺少 relay 候选**；
  - iceServers 来自 `pair.ok.turn` / `relay.alloc.turn`；**首次 gather 即含 TURN 候选**（单阶段 ICE）；
  - 创建两条 `DataChannel` → gather 完成（非 trickle）→ 发 `punch.offer` → 收 `punch.answer` → `setRemoteDescription` → 等连接建立；
- **DataChannel 由插件（offer 方）创建**；手机作为 answerer 只能 `onDataChannel` 接收；
- **自发重发 `punch.offer` 之间 MUST ≥2s**；由 `punch.request` 触发的 offer **不受该窗口约束**（契约 §4.1/§3.5）；
- 收到 `bye`（契约 §4.3 条件①）/ 被 dispose 时按 §2.2 处理；收到 `PAIR_REPLACED`（条件⑤，该手机已在另一台电脑完成配对）或其 `punch.offer` 被回 `PAIR_NOT_FOUND`（pair 已销毁后的过期 offer，02 §3.2 告警路径）→ 同样按 §2.2 清理隧道；**三者之后插件均回到未配对状态**：生成新 `pair_token` → `pair.ready` → `pair.ready.ok` → 恢复 QR 轮印（`pair` 已销毁，§4.3 的"pair.ok 后不重印"约束解除；E10 ⑦ 是本条的验收条件）。`presence` 仅记日志（A5 用户批复：自发重发遇 `PEER_OFFLINE` 的暂停机制暂不做）。

### 4.5 approve.js — N3 预留（本期只占位）

```js
// v1: 仅调试日志，不做任何应答（应答由官方前端负责）
ctx.on('approval/request', async (req, next) => { log.debug('approval', req); return next() })
```

- **【已核实】** `approval/request` 是 **waterfall 监听器**（返回即应答，`next()` 表示委托），服务名就是 **`approval`**（`dsh-base/cordis.patch.yml` 中 `id: approval` 行为启用状态），因此 N3 改为 `inject` 追加 `'approval'` 可用，stub 写法正确；
- 注意：把服务加进 `inject` 后，**组合缺该服务会导致 DSH 启动失败**（见 §2 的 pending 说明）。web profile 已含该行，安全。

## 5. 关键流程时序

```
DSH 启动 → apply(): 载入密钥/证书 → 连 Bridge → hello(boot_id) → 上线
         → 生成 pair_token → pair.ready → pair.ready.ok → 取 launch token → 打印 QR
手机扫码 → Bridge pair.ok（含 TURN 凭证）→ 手机 punch.request → 插件发 punch.offer
         → 手机回 punch.answer → ICE/DTLS（单阶段 ICE；手机 pin 插件证书指纹）
两条 DataChannel 开 → 手机发 OPEN(authority) → 插件 net.connect(转发目标) → 双向泵字节
手机断开 → DataChannel close → 全部 socket 销毁 → pair 保留（24h 内回来免扫码）
插件网络抖动 → boot_id 不变 → pair 保留 → 重连后主动重发 punch.offer → 快速重建（<5s）
隧道因链路死 → ICE 主触发或 15s 兜底 → 销毁重建（stream_id 从 1 重启）
DSH 重启（新进程，boot_id 变）→ pair 销毁 → 新 QR → 手机收 AGENT_RESTARTED → 重新扫码
手机换绑他机（条件⑤）→ 旧 agent 收 PAIR_REPLACED → 拆隧道 → 恢复未配对 → 恢复 QR 轮印
用户正常关闭 DSH → 进程退出路径发 bye（await，尽力而为）→ Bridge 立即销毁 pair
plugins 热重载 → fiber dispose，不发 bye → 依赖 boot_id 在 24h 内恢复（E10 断言 <6s）
```

## 6. launch token 流程（契约 §2 `t` 字段）

- **推荐做法（省掉手工拷贝）**：`inject` 已含 `connection`，直接调用

  ```js
  const url = ctx.connection.authenticatedUrl(`http://127.0.0.1:${ctx.webServer.port}/`)
  const token = new URL(url).searchParams.get('token')
  ```

  该 API 已核实：`HostConnectionService` 的服务名就是 `connection`，`authenticatedUrl()` 委托 `BrowserAuth` 把**本进程**的 launch token 拼进 URL。**全程在内存内，不落盘、不需用户操作，且每次装配都取到当次进程的 token。**
- **兜底做法**：`DSML_LAUNCH_TOKEN` 环境变量或控制台粘贴。仅当上述 API 不可用时使用（注意：token 由进程启动后生成，**用户无法在启动前预知**，所以环境变量只能靠"先跑一次看到值 → 带上重启"，而重启会生成新 token → **基本不可用**，仅作最后手段）；
- 红线：token 不写日志、不落盘、不进 `pair.ready`（只进 QR）；其可用窗口由 `pt` 的 5min TTL 约束。

## 7. 配置（环境变量）

| 变量 | 默认 | 说明 |
|---|---|---|
| `DSML_SIGNAL_URL` | 必填 | **主机名**（如 `bridge.example.com`），不是完整端点。插件拼接为 `wss://<值>/v1/signal`。若填成 `wss://host/v1/signal` 会拼出 `/v1/signal/v1/signal` → 装配期 **fail-fast** 校验 |
| `DSML_AUTHORITY` | `127.0.0.1:13080` | **手机侧** authority（契约 §1 固定值）。**若与契约固定值不一致，装配期 fail-fast**——它不是可自由调整的运维参数（改它会使全体 cookie 失效并使 OPEN 断言失败） |
| `DSML_FORWARD_TARGET` | 由 `ctx.webServer.port` 推导；兜底 `127.0.0.1:3080` | PC 侧 DSH 端口，插件的 `net.connect` 目标 |
| `DSML_LAUNCH_TOKEN` | 空 | 仅兜底（§6），正常路径不使用 |
| `DSML_LOG_LEVEL` | `info` | 日志级别 |
